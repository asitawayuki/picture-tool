# 出力幅の上限指定（`--max-width`）設計

作成日: 2026-08-12
レビュー反映: 2026-08-12（`docs/tmp/review.md`）

## 1. 背景と目的

pad モードは元画像の画素数をそのまま保ち、余白を足して 4:5 にするだけである。
crop モードも同様に、中央を切り出すだけで解像度は落とさない。

その結果、高画素機（例: 61MP / 9504×6336）では出力が

- pad → 9504×11880
- crop → 5069×6336

となり、SNS 側の画素数制限に引っかかる。**出力 4:5 キャンバスの幅に上限を設けて
縮小できるようにする**のがこの機能の目的である。

> **動機の出典について**: 「SNS の画素数制限」は利用者の申告であり、具体的なサービス名・
> 制限値・踏んだ症状は未確定である（2026-08-12 時点で「まだ決めていない」）。
> この機能はオプトインかつ値を利用者が決めるため、前提が外れても設計は壊れない。
> ただし GUI にプリセット値（1080 / 1440 等）を出すかどうかの判断は、
> 実際に使う値が定まるまで保留する。**本設計では数値入力のみを提供する。**
>
> なお、制約が画素数ではなく**ファイルサイズ**だった場合は、このツールが既に持つ
> `--max-size` が担当する。`--max-width` は画素数側の独立した軸である。

副次的な効果として、Exif フレーム描画時のメモリ使用量が大きく下がる。現状は
9504×11880 の RGBA キャンバス（約 450MB）を確保してから文字とロゴを描いており、
`process_batch` は rayon で並列に走るためワーカー数だけ同時に確保される。

## 2. スコープ

| 項目 | 決定 |
|---|---|
| 指定方法 | **幅を px で指定**。出力は常に 4:5 なので高さは `幅 × 5/4` で確定する |
| 対象モード | **pad と crop**。quality モードは対象外（無視することを明示的に通知する） |
| 拡大 | **しない**。指定値は上限であり、元がそれより小さければそのまま |
| 既定値 | **無指定 = 無制限**（従来どおり原寸） |
| CLI | `--max-width <px>` |
| GUI | 「出力幅を制限する」トグル + 幅入力 |

quality モードを対象外にした理由: このモードはアスペクト比を変えないため、「幅」を
指定しても縦写真では長辺が `幅 × 5/4` を大きく超えてしまい、上限としての意味を持たない。
quality モードに上限を設けるなら「長辺の上限」という別の仕様が必要であり、
本設計には含めない。

**ただし黙って無視はしない。** §3 で「上限を指定したのに無制限で処理された」を
サイレント失敗として避けている以上、モード不一致による無視も同じ扱いにする必要がある。
CLI は起動時に1回警告する（`--exif-frame` を非 pad で使ったときの既存の前例と同じ形。
`cli/src/main.rs:82-87`）。GUI はトグルを**隠さず無効化して理由を表示する**。

> 背景色を pad 限定で隠しているのとは区別する。背景色は他モードには概念自体が無い
> パラメータだが、`max_width` は「上限」であり、効いていないことに気づけないと
> 機能の目的そのものを損なう。

## 3. データモデルと幅の正規化

`ProcessingConfig` にフィールドを1つ追加する。

```rust
/// 出力 4:5 キャンバスの幅の上限 (px)。None なら無制限（元の画素数を保つ）。
/// 実効値は 4 の倍数に切り捨てられる。
#[serde(default)]
pub max_width: Option<u32>,
```

`#[serde(default)]` を付けるのは、GUI から来る JSON にこのフィールドが無くても
デシリアライズが壊れないようにするため（既存の `warnings` / `size_limit_exceeded`
と同じ扱い）。

正規化は1関数に閉じ込める。

```rust
/// 目標キャンバスサイズ。キャンバスは常に k*4 × k*5（S4 で確立した不変条件）。
/// `max_width` が 4..=20000 に収まっていることは `validate_config` が保証するので、
/// ここは丸めだけを行い判定はしない。
fn target_canvas(max_width: Option<u32>) -> Option<(u32, u32)> {
    let k = max_width? / 4;            // 切り捨て
    Some((k * 4, k * 5))
}
```

| 指定 | 実効キャンバス | 備考 |
|---|---|---|
| 1080 | 1080×1350 | Instagram 推奨値 |
| 1000 | 1000×1250 | |
| 1002 | 1000×1250 | 切り上げない |
| 3 以下 / 20001 以上 | （エラー） | `validate_config` で弾く |

**切り捨てが唯一正しい丸め方向である。** この機能の目的は「指定値を超えないこと」
なので、切り上げて 1002 → 1004 になったら機能が目的を果たしていない。

丸めが起きたことの通知は入口で行う。core は `eprintln!` しない規約があり、かつ
画像ごとの `ProcessResult.warnings` に積むと同じ文言が画像数だけ並ぶだけなので、

- **CLI**: 起動時に1回だけ stderr へ出す
- **GUI**: 入力確定時に値を 4 の倍数へスナップし、切り捨て後の値だけを表示する

という分担にする。core は黙って正規化するだけで警告を持たない。

## 4. パイプライン統合

```
open → apply_orientation
     → [前段 / pad のみ] 目標があり fit_to_4_5(w, h).0 > target_w なら
                        写真を目標ボックスへ縮小（Lanczos3）
     → match mode { Crop | Pad(+frame) | Quality }   ← 中身は無変更
     → [最終] 目標があり canvas_w > target_w なら resize_exact(target)（Lanczos3）
     → encode
```

前段・最終とも**縮小方向にしか働かない**。前段は `fit_to_4_5(w, h).0 > target_w`、
最終は `canvas_w > target_w` がガードで、どちらも満たさなければ何もしない。
これが §2 の「拡大しない」を実装レベルで担保する。

### 契約は等値ではなく不等式

**保証するのは「出力キャンバス幅 ≤ 目標幅」である。** 元画像が小さければ出力も小さい
ままで、目標へ引き伸ばすことはしない。

そのうえで、**目標より大きい入力に対しては目標幅ちょうどに着地する**ことが算術的に
導ける。前段のスケールは `target_w / fit_to_4_5(w, h).0` であり、元キャンバスと写真の
差は最大 3px（`fit_to_4_5` の `k` の切り上げ分）なので、スケール後の差は 1px 未満に潰れる。
したがって縮小後の写真幅 `w'` は `target_w - 1 ≤ w' ≤ target_w` に収まり、
`k = ceil(w'/4)` は `target_w/4` に一意に定まる。縦位置の写真は高さが `k` を決めるが
同じ議論が成り立つ。テストではこの等値をピン留めする（§9 の #1 / #2）。

### 前段を pad だけに限定する理由

前段の狙いは「巨大な RGBA キャンバスを確保してその上に文字とロゴを描く」コストを
避けることであり、それが起きるのは pad（特に Exif フレーム）だけである。

crop は `crop_imm` で元より小さいバッファしか作らない。ここで前段縮小を入れると、
切り落として捨てる画素（3:2 横位置なら約半分）まで Lanczos3 で再サンプルすることになる。
**crop → 最終縮小の順の方が安く、丸めも一度で済む。**

### なぜ最終ステップが必要なのか

前段だけでは上限を保証できない。検証した範囲では前段の fit だけで目標値に着地するが、
Exif フレームはバーを収める余白が足りないときにキャンバスを `div_ceil(5) * 5` で
拡張する経路を持っており（`layout.rs` の `calculate_pad_exif_layout`）、
ここが目標を超え得る。crop に至っては前段が無いので最終がすべてを担う。

最終の `resize_exact` は保険ではなく**契約**である。

> 画質を理由に2段構えを選んだわけではない。むしろ「大きく描いてから縮小」は
> スーパーサンプリングとして働くので、画質だけを見れば最終リサイズ一本の方が有利ですらある。
> 同梱ロゴは sony / fujifilm が SVG（`target_size` で直接ラスタライズ）、
> gmaster.png は 2880×1748 で、ロゴ読み込みサイズ `min(exif_area_h, exif_area_w) * 3/5`
> （`mod.rs:262`）は 9504 幅キャンバスでも 228px 程度にしかならない。拡大は起きない。
> **2段構えの根拠はメモリのみ**である。

### 併せて直す1点

`convert_aspect_ratio_pad` は `fit_to_4_5` を使わず自前で `width / 0.8` を計算しており、
**4:5 が厳密にならない**。さらに `|current_ratio - 0.8| < 0.001` の早期 return があり、
この帯に入る入力は現在パディングされず素通りする。

前段のスケール計算が「pad が作るキャンバス幅」に依存する以上、その答えが2つある状態は
事故のもとなので、`convert_aspect_ratio_pad` を `fit_to_4_5` に寄せる。

**影響は 1px では収まらない。** 早期 return の帯に入る「ほぼ 4:5」の入力では、
出力寸法が画像サイズに比例して変わる。

| 入力 | 現状 | 修正後 |
|---|---|---|
| 4000×5001 | 4000×5001（素通り。`4000*5 ≠ 5001*4`） | 4004×5005（`4004*5 = 5005*4`） |
| 8000×10020 | 8000×10020（素通り） | 8016×10020 |

過去バッチを再実行すると差分が出る。**利用者に確認のうえ許容と判断した**（2026-08-12）。
厳密な 4:5 に近づく方向の変化であり、S4 で確立した `k*4 × k*5` の不変条件に一本化できる。

既存の pad テストは比率の許容が `0.02`（`lib.rs:909`）でこの差を検出できないため、
§9 の #5 で `fit_to_4_5` の値との一致に置き換える。

> `convert_aspect_ratio_crop` にも同種の非厳密さがあるが、前段が pad 限定になったことで
> crop のキャンバス幅に依存しなくなったため、今回は触らない。

## 5. CLI

```rust
/// 出力4:5キャンバスの幅の上限 (px)。無指定なら元の画素数を保つ
#[arg(long, value_parser = clap::value_parser!(u32).range(4..=20000))]
max_width: Option<u32>,
```

**境界を設ける必要がある理由**は u32 オーバーフローである。`k * 5`（`k = 幅 / 4`）は
幅が u32 の上限付近だと溢れる。**20000 という値の根拠**はメモリで、
20000×25000 の RGBA キャンバスで約 2GB に達する。100MP 中判機の 4:5 キャンバス幅でも
11648px なので、実用上の制約にはならない。

起動時に1回だけ stderr へ出すもの:

- 4 の倍数でない指定を受けたときの実効値
- quality モードで `--max-width` を指定したとき（`--exif-frame` の既存警告と同じ形）

## 6. GUI

- `types.ts` の `ProcessingConfig` に `max_width: number | null` を追加
- `App.svelte` の既定値は `null`
- `SettingsPanel.svelte` に「出力幅を制限する」チェックボックスと
  `<input type="number" min="4" max="20000">` を追加。右に確定サイズ（`→ 1080×1350`）を
  常時表示する
- **入力確定時（change）に値を 4 の倍数へスナップする。** `step="4"` はスピナーと
  HTML バリデーションにしか効かず、`1002` を直接入力・貼り付けできてしまうため予防にならない。
  スナップすれば表示値・送信値・Rust の正規化結果がすべて一致し、`target_canvas` の
  切り捨てを TS 側に再実装して drift させることもない（確定サイズ表示はスナップ後の値から
  `幅 × 5/4` を出すだけになる）
- quality モード時は**トグルを隠さず無効化し、理由を併記する**（§2 参照）
- 変換系コマンド（`commands.rs:224` 付近）は**変更不要**。`core::ProcessingConfig` を
  そのまま serde で受けており、`validate_config` も既に呼んでいる
- 新規 Tauri コマンドを追加しないため、`gui/src/security.rs` の検証対象
  （パス・フォント名・プリセット名）には触れない。プレビューコマンドは引数が1つ増えるが、
  数値なので検証は `validate_config` で足りる

### Exif フレームのプレビュー

`render_exif_frame_preview` コマンド（`commands.rs:544`）は長辺 **400px** 固定で
`generate_exif_frame_preview_base64` を呼んでいる。`max_width` に 400 未満の値を
指定すると、実出力では §8 の閾値効果でフレームが消えるのにプレビューには出る、
という**この機能が新設する乖離**が生じる。

`render_exif_frame_preview` に目標幅を渡し、`min(400, target_w)` にクランプして揃える。

> これで解消するのは新設分だけである。プレビューが 400px 固定である以上、
> 実出力（1080 など）との間には元々ズレがあり、しかも §8 の閾値は小さいほど
> `skip_exif` に落ちやすいので**プレビューの方が悲観的**に出る。この既存の近似は
> 本設計では触らない。

## 7. エラー処理

| 事象 | 扱い |
|---|---|
| `max_width` が 4 未満 / 20000 超 | `validate_config` でエラー。CLI は clap も弾く。GUI は invoke が Err |
| 4 の倍数でない | 切り捨てて正規化。CLI は起動時に1回 stderr、GUI は入力確定時にスナップ |
| quality モードで指定 | 無視するが黙らない。CLI は起動時に1回 stderr、GUI はトグルを無効化して理由表示 |
| 元画像が指定より小さい | 何もしない（正常系。警告なし） |
| 縮小の結果 Exif フレームが描けなくなった | §8 のとおり `ProcessResult.warnings` に積む |

## 8. 縮小によって Exif フレームが消える問題

Exif フレームのレイアウト閾値は**絶対 px** である（`layout.rs`）。

| 定数 | 値 | 意味 |
|---|---|---|
| `MIN_SHORT_SIDE` | 200 | 写真の短辺がこれ未満ならフレームを描かない |
| `EXIF_BAR_MIN_PX` | 30 | バー厚の下限 |
| `MAX_SHRINK_RATIO` | 0.20 | これを超える写真縮小が必要ならフレームを描かない |

したがって前段縮小の結果は「同じ絵の縮小版」にはならない。例えば `9504×1600` の
パノラマに `max_width=1080` を指定すると写真が `1080×182` になり、短辺 200px 未満で
`skip_exif` に落ちてフレームが消える。`max_width` 無しなら短辺 1600 でフレームは出るので、
**この引き金は本機能が新設するものである**。現状 `render_exif_frame` は `skip_exif` 時に
何も伝えずキャンバスを返すため、利用者はフレームが消えたことに気づけない。

### 対応

`render_exif_frame` の戻り値を変更し、`skip_exif` に落ちたことを呼び出し元へ伝える。

```rust
pub struct ExifFrameOutput {
    pub image: DynamicImage,
    pub warnings: Vec<String>,
}

pub fn render_exif_frame(...) -> Result<ExifFrameOutput>
```

`process_image` は `warnings` を `ProcessResult.warnings` に連結する。これは core の
既存規約（core は `eprintln!` せず `warnings` に積む）にそのまま乗る形であり、
CLI は stderr、GUI は `ResultDialog` に**追加実装なしで**出る。

`max_width` 指定の有無にかかわらず `skip_exif` は警告対象にする。小さい画像で黙って
フレームが消える既存の挙動も同時に解消される。

`render_exif_frame` は CLAUDE.md の Core API 表に載っているため、そちらの更新も必要。
呼び出し元は `process_image` と `generate_exif_frame_preview_base64` の2箇所。

## 9. テスト

テストを書く前に `test-integrity` スキルを起動する（CLAUDE.md 規約）。
実装ではなく**仕様から**ケースを導く。

| # | 検証内容 |
|---|---|
| 1 | pad + `max_width=1080`、目標より大きい入力 → 厳密に 1080×1350（`w*5 == h*4` も assert） |
| 2 | crop + `max_width=1080`、目標より大きい入力 → 同上 |
| 3 | 800×533 の入力 + `max_width=1080` → 800×1000 のまま（**拡大しない**）。契約は不等式なので等値は要求しない |
| 4 | `max_width=1002` → 1000×1250（切り上げず、指定値を超えない） |
| 5 | `max_width=None` → `fit_to_4_5(w, h)` の値と一致（`convert_aspect_ratio_pad` 統一後の回帰） |
| 6 | quality モードでは出力寸法が変わらない |
| 7 | Exif フレーム + `max_width` → キャンバスが厳密に目標サイズ。**前提条件として「`skip_exif` に落ちていない＝バーが実際に描かれている」も同時に assert する** |
| 8 | `validate_config`: `Some(3)` と `Some(20001)` はエラー / `Some(4)` と `Some(20000)` は OK |
| 9 | `9504×1600` + `max_width=1080` → フレームが消えたことが `ProcessResult.warnings` に載る |

7 の前提条件 assert は過去に踏んだ罠への対策である。S4 で「重ならないこと」を検査する
テストが、そもそも検査対象の状況を作れておらず、バグを入れ直しても green のままだった。
否定形・不変条件を検査するテストには、検査対象が実際に発生していることの assert を添える。

9 は 7 の裏返しであり、**両方あって初めて `skip_exif` の境界が仕様として固定される**。
