# 出力幅の上限指定（`--max-width`）設計

作成日: 2026-08-12

## 1. 背景と目的

pad モードは元画像の画素数をそのまま保ち、余白を足して 4:5 にするだけである。
crop モードも同様に、中央を切り出すだけで解像度は落とさない。

その結果、高画素機（例: 61MP / 9504×6336）では出力が

- pad → 9504×11880
- crop → 5069×6336

となり、SNS 側の画素数制限に引っかかる。**出力 4:5 キャンバスの幅に上限を設けて
縮小できるようにする**のがこの機能の目的である。

副次的な効果として、Exif フレーム描画時のメモリ使用量が大きく下がる。現状は
9504×11880 の RGBA キャンバス（約 450MB）を確保してから文字とロゴを描いており、
`process_batch` は rayon で並列に走るためワーカー数だけ同時に確保される。

## 2. スコープ

| 項目 | 決定 |
|---|---|
| 指定方法 | **幅を px で指定**。出力は常に 4:5 なので高さは `幅 × 5/4` で確定する |
| 対象モード | **pad と crop**。quality モードは対象外 |
| 拡大 | **しない**。指定値は上限であり、元がそれより小さければそのまま |
| 既定値 | **無指定 = 無制限**（従来どおり原寸） |
| CLI | `--max-width <px>` |
| GUI | 「出力幅を制限する」トグル + 幅入力（pad / crop のときだけ表示） |

quality モードを対象外にした理由: このモードはアスペクト比を変えないため、「幅」を
指定しても縦写真では長辺が `幅 × 5/4` を大きく超えてしまい、上限としての意味を持たない。
quality モードに上限を設けるなら「長辺の上限」という別の仕様が必要であり、
本設計には含めない。

## 3. データモデルと幅の正規化

`ProcessingConfig` にフィールドを1つ追加する。

```rust
/// 出力 4:5 キャンバスの幅の上限 (px)。None なら無制限（元の画素数を保つ）。
/// 実効値は 4 の倍数に切り捨てられる。
#[serde(default)]
pub max_width: Option<u32>,
```

`#[serde(default)]` を付けるのは、GUI から来る JSON にこのフィールドが無くても
デシリアライズが壊れないようにするため（既存の `warnings` / `size_limit_exceeded`
と同じ扱い）。

正規化は1関数に閉じ込める。

```rust
/// 目標キャンバスサイズ。キャンバスは常に k*4 × k*5（S4 で確立した不変条件）。
///
/// `max_width` が 4..=20000 に収まっていることは `validate_config` が保証する。
/// ここで範囲外を None に落とすと「上限を指定したのに無制限で処理された」という
/// サイレントな失敗になるため、丸めだけを行い判定はしない。
fn target_canvas(max_width: Option<u32>) -> Option<(u32, u32)> {
    let k = (max_width? / 4).max(1);   // 切り捨て
    Some((k * 4, k * 5))
}
```

| 指定 | 実効キャンバス | 備考 |
|---|---|---|
| 1080 | 1080×1350 | Instagram 推奨値 |
| 1000 | 1000×1250 | |
| 1002 | 1000×1250 | 切り上げない |
| 3 以下 / 20001 以上 | （エラー） | `validate_config` で弾く |

**切り捨てが唯一正しい丸め方向である。** この機能の目的は「指定値を超えないこと」
なので、切り上げて 1002 → 1004 になったら機能が目的を果たしていない。

丸めが起きたことの通知は入口で行う。core は `eprintln!` しない規約があり、かつ
画像ごとの `ProcessResult.warnings` に積むと同じ文言が画像数だけ並ぶだけなので、

- **CLI**: 起動時に1回だけ stderr へ出す
- **GUI**: 入力欄を `step="4"` にして、そもそも半端な値を作らせない

という分担にする。core は黙って正規化するだけで警告を持たない。

## 4. パイプライン統合

`process_image` の変換部分だけが変わる。

```
open → apply_orientation
     → [前段] 目標があり、現在の 4:5 キャンバス幅が目標幅を超えるなら
              写真を縮小（Lanczos3 / 拡大はしない）
     → match mode { Crop | Pad(+frame) | Quality }   ← 中身は無変更
     → [最終] キャンバスが目標と一致しなければ resize_exact
     → encode
```

前段の縮小率は「そのモードが今のままなら作るキャンバスの幅」から逆算する。

| モード | リサイズ前のキャンバス幅 | 前段の scale |
|---|---|---|
| Pad | `fit_to_4_5(w, h).0` | `target_w / canvas_w` |
| Crop | `min(w, round(h * 4/5))` | 同上 |
| Quality | — | 対象外（素通り） |

### なぜ前段と最終の2段構えなのか

**前段だけでは上限を保証できない。** 検証した範囲では前段の fit だけで目標値ちょうどに
着地するが、それは `fit_to_4_5` の `k` の丸めの副産物であって構造的な保証ではない。
特に Exif フレームは、バーを収める余白が足りないときにキャンバスを
`div_ceil(5) * 5` で拡張する経路を持っており（`layout.rs` の
`calculate_pad_exif_layout`）、ここが目標を超え得る。

**最終だけでは前段の利点を失う。** 巨大キャンバスを一度作るコストが残り、
ロゴ PNG を 1900px 相当まで拡大してから 216px へ縮小することになって輪郭が甘くなる。

したがって最終の `resize_exact` は保険ではなく**契約**として置く。通常は前段が
正しく効いて no-op になる。

### 併せて直す1点

`convert_aspect_ratio_pad` は `fit_to_4_5` を使わず自前で `width / 0.8` を計算しており、
**4:5 が厳密にならない**。例: 幅 1079 → 高さ 1349 で `1079*5 = 5395 ≠ 1349*4 = 5396`。
Exif フレーム経路だけが S4 で `k*4 × k*5` に統一され、素の pad は取り残されていた。

前段の scale 計算が「pad が作るキャンバス幅」に依存する以上、その答えが2つある状態は
事故のもとなので、`convert_aspect_ratio_pad` を `fit_to_4_5` に寄せる。既存出力への
影響は最大 1px、かつ厳密な 4:5 に近づく方向のみ。

## 5. CLI

```rust
/// 出力4:5キャンバスの幅の上限 (px)。無指定なら元の画素数を保つ
#[arg(long, value_parser = clap::value_parser!(u32).range(4..=20000))]
max_width: Option<u32>,
```

上限 20000 は安全弁である。`k * 5` を u32 で計算するため極端な値はオーバーフローする。
拡大しない仕様なので大きい値は実質 no-op だが、黙って壊れるより弾く。100MP 中判機の
4:5 キャンバス幅でも 11648px なので実用上の制約にはならない。

4 の倍数でない指定を受けたときは、実効値を起動時に1回だけ stderr へ出す。

## 6. GUI

- `types.ts` の `ProcessingConfig` に `max_width: number | null` を追加
- `App.svelte` の既定値は `null`
- `SettingsPanel.svelte` に「出力幅を制限する」チェックボックスと
  `<input type="number" step="4" min="4">` を追加。右に確定サイズ（`→ 1080×1350`）を
  常時表示する。**crop / pad のときだけ**表示する
- `gui/src/commands.rs` は**変更不要**。`core::ProcessingConfig` をそのまま serde で
  受けており、`validate_config` も既に呼んでいる（`commands.rs:224`）
- 新規 Tauri コマンドを追加しないため、`gui/src/security.rs` の検証対象
  （パス・フォント名・プリセット名）には触れない
- Exif フレームのプレビューは既に 1024px 以下へ縮小してから描画しているので変更不要。
  むしろプレビューと実出力が近づく方向に働く

## 7. エラー処理

| 事象 | 扱い |
|---|---|
| `max_width` が 4 未満 | `validate_config` でエラー。CLI は起動時に失敗、GUI は invoke が Err |
| `max_width` が 20000 超 | CLI は clap が弾く。GUI は `validate_config` で弾く |
| 4 の倍数でない | 切り捨てて正規化。CLI は起動時に1回 stderr、GUI は `step="4"` で予防 |
| 元画像が指定より小さい | 何もしない（正常系。警告なし） |

## 8. 既知の相互作用（記録のみ、対応しない）

`--max-width 200` のような極端に小さい値を指定すると、Exif フレームが
「短辺 200px 未満なら描画しない」（`layout.rs` の `MIN_SHORT_SIDE`）経路に落ち、
フレームが黙って消える。これは既存の挙動であり、この機能が新たに作る問題ではない。
Exif フレームを使う実用的な幅（1080 以上）では発生しない。

## 9. テスト

テストを書く前に `test-integrity` スキルを起動する（CLAUDE.md 規約）。
実装ではなく**仕様から**ケースを導く。

| # | 検証内容 |
|---|---|
| 1 | pad + `max_width=1080` → 出力が厳密に 1080×1350（`w*5 == h*4` も assert） |
| 2 | crop + `max_width=1080` → 同上 |
| 3 | 800×533 の入力 + `max_width=1080` → 800×1000 のまま（拡大しない） |
| 4 | `max_width=1002` → 1000×1250（切り上げず、指定値を超えない） |
| 5 | `max_width=None` → 従来どおり原寸キャンバス（回帰） |
| 6 | quality モードでは無視される |
| 7 | Exif フレーム + `max_width` → キャンバスが厳密に目標サイズ。**前提条件として「`skip_exif` に落ちていない＝バーが実際に描かれている」も同時に assert する** |
| 8 | `validate_config`: `Some(3)` と `Some(20001)` はエラー / `Some(4)` と `Some(20000)` は OK |

7 の前提条件 assert は過去に踏んだ罠への対策である。S4 で「重ならないこと」を検査する
テストが、そもそも検査対象の状況を作れておらず、バグを入れ直しても green のままだった。
否定形・不変条件を検査するテストには、検査対象が実際に発生していることの assert を添える。
