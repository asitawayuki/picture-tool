[メタデータ編集 spec](2026-08-18-metadata-editing-design.md)。本 spec が持つのは

**改訂**: 独立レビュー 2 巡（`docs/tmp/review.md` の R-01〜R-15、

## 背景と目的

3,000 枚のフォルダーを開いて「Instagram に上げる数枚」を選ぶのに、グリッドを
スクロールして探すしかない。欲しいのは 2 つ:

- 名前で絞る・日付順で見る（**Phase 1**）
- **★で絞る**（**Phase 2**）── 情報モードで付けた★は既に元ファイルに保存されている
  のに、それを使って一覧を絞る手段が無い

★の絞り込みには「フォルダー全体の★を知る」ことが要る。ところが現行の★読み取りは
**1 枚ごとにファイル全体をメモリに読む**（`core::metadata::read_metadata` の
`std::fs::read`）。5MB の JPEG から★1つを取るために 5MB 読んでいる。
`browser/ratings.svelte.ts` が「可視範囲だけ読む」と明示して設計されているのは
そのコストが理由であり、★で絞り込むにはこの前提を反転させることになる。

**そこで先に実測した。** 数字は「実測」節にある。設計はその数字から決めた。

## スコープ

### やること

| 項目 | 内容 |
|---|---|
| Phase 1 | ファイル名の部分一致検索、名前 / 更新日 / 作成日の昇順・降順 |
| Phase 2 | ★の絞り込み（名前付き 7 択）。★はフォルダーを開いた時点で全件揃う |
| 読み取り | JPEG の先頭だけを読む軽量経路を core に置く。**読む側は全部 1 つの入口を通す**（読めなければ全体読みへフォールバック） |
| 並列化 | `list_images` を `par_iter` にする（いまは逐次。実測で 4.4 倍の差） |
| ヘッダー | 段の作り方を明示し、Phase 1 が持ち込んだ最小幅の破綻を直す |
| 一貫性 | 絞り込みは**表示だけ**を変える。選択は解除せず、変換対象からも減らさない |

### やらないこと

| 項目 | 理由 |
|---|---|
| 撮影日での絞り込み・並び替え | Exif `DateTimeOriginal` の解釈（タイムゾーン・サブ秒・機種差）が別の設計になる。更新日／作成日は `stat` だけで足りるので Phase 1 に入れた |
| 再帰的なフォルダー走査 | `list_images` が直下のみなのは GUI の初期設計からの一貫した方針。ここで変えない |
| グリッドから直接★を付ける | ★の書き込みは情報モードの承認フロー（フォルダー単位の OS ダイアログ）を通る。グリッドのクリック 1 つで元ファイルを書き換える経路は作らない |
| タイトル・コメントでの検索 | 全件のタイトルを持つことになり、★1つとは規模が違う。要望が出てから |
| ★の索引を永続キャッシュする | レビューの案 B。索引が節約するのは 68〜202ms でしかなく、ディスク上の状態・無効化・破損という新しい失敗モードに見合わない。**初回が十分速いので出番が来ていない** |
| 絞り込み条件の永続化（`localStorage`） | Phase 1 で「フォルダーを変えても保つが、アプリを閉じたら消える」と決めた。起動直後に空でないグリッドが出ない方が事故が少ない |

## 実測（spike）

`core/tests/rating_scan_spike.rs`（`#[ignore]`。実写真が要るので通常のテスト実行では
走らない）。**クレートを上げたときの再測定に使うので消さない。**

### 測った環境

Fedora / Linux 7.1.12 / btrfs（`compress=zstd:1`）/ NVMe / 20 コア / RAM 62GB。
コーパスは実写真 1 枚（5.72MB、Exif APP1 11.6KB ＋ XMP APP1 15.7KB）を複製した
1,006 枚（5.75GB）と 5,006 枚（28.6GB）。★あり 838 枚 / なし 168 枚を混ぜてある。

### 読み取り経路の比較（**rayon 並列** / コールドキャッシュ / 3 回の中央値）

| 経路 | 1,000 枚 | 5,000 枚 | ピーク RSS |
|---|---|---|---|
| **A**: 現行 `read_metadata`（全体を読む） | 1,118 ms | 4,978 ms | 201 MB |
| **B**: SOI〜SOS だけ読む | **68 ms** | **202 ms** | **7.4 MB** |
| B': 前方 64KB を一括で読む | 79 ms | 232 ms | 7.1 MB |
| （参考）I/O のみ・全体を読む | 1,104 ms | 5,147 ms | — |
| （参考）I/O のみ・先頭だけ読む | 56 ms | 304 ms | — |

読む量は**全体の 0.48%**（1 枚 5.72MB のうち SOI〜SOS が 26.8KB）。

**この機能は I/O 律速である。** A ≒「I/O のみ・全体」、B ≒「I/O のみ・先頭」で、
解析（`little_exif` ＋ `img_parts` ＋ `quick-xml`）のコストは差に現れない。
つまり速くする方法は「読む量を減らす」しかなく、解析側を触る意味は無い。

5,000 枚では**ウォームでも A は 4,567ms**（28.6GB がページキャッシュに載らない）。
B は 104ms。フォルダーが大きいほど差が開く。

### `list_images` に★を畳んだ場合（1,000 枚 / コールド / 3 回の中央値）

**並列と逐次の両方を載せる。** `list_images` は**いま逐次ループ**（`commands.rs:93` の
`for file_path in direct_files`）で、`par_iter` を使っているのは `read_image_ratings`
だけである。並列の数字だけを見て設計すると、本番の形に移らない（R-01）。

| 経路 | 逐次（**いまの `list_images` の形**） | rayon 並列 |
|---|---|---|
| L: `list_images` 相当（★を読まない） | 576 ms | 132 ms |
| L+B: ★を畳んだ `list_images` | 650 ms | 169 ms |
| 畳んだことによる増分 | +74 ms（+13%） | +37 ms（+28%） |

`list_images` は 1 枚あたり `image::image_dimensions`（open）＋ `read_exif_info`（open）
＋ `fs::metadata` を回す（`core/src/lib.rs:580`）。★を足すと open が 3 回になる。

**設計の帰結**: `list_images` を `par_iter` にすれば、★を畳んでも
**576ms → 169ms** で**現行より速くなる**。並列化しないと 576ms → 650ms の純粋な悪化。
→ 設計 §1 で並列化を決めている。

### 計測の罠（同じ実測をやり直す人向け）

**どれも潰さないと逆の結論が出た。**

1. **btrfs の reflink**。`std::fs::copy` は Linux で `copy_file_range` に落ち、btrfs は
   それを CoW の共有で満たす。1,000 枚が同じ物理ブロックを指すので、コールドの
   つもりの走査が 2 枚目以降すべてキャッシュヒットになり、**軽量経路の効果が
   実際より小さく出る**。`filefrag -v` で物理ブロックが一致し `shared` が付くのが
   その状態。コーパスは種をメモリに載せて 1 枚ずつ実体を書く
2. **計測順序の汚染**。コールド計測の直後にウォームを測ると、ウォームの 1 本目だけ
   実質コールドになる（コールド計測は先頭しか読んでいないため）。最初の実測では
   「I/O のみ」のウォームが A のウォームより 4 倍遅いという矛盾した数字が出た。
   ウォームの前に全件を読んで暖める
3. `BufReader` の `Seek::seek` はバッファを無条件に捨てる。飛ばした先を読むために
   同じ 64KB を読み直すので、`seek_relative` を使う（B が B' の 2 倍遅かった原因）
4. **並列と逐次を取り違えない**。spike は両方を出力する。本番のコードがどちらの形かを
   確かめてから数字を引く（R-01 がまさにこれ）

### この実測が示していないこと

- **コーパスは実写真 1 枚の複製**。SOI〜SOS の大きさは 26.8KB で一定であり、
  **機種ごとの分布は分かっていない**。B は分布に依存しない（SOS まで辿るだけ）が、
  B' の `PREFIX` を選ぶ根拠には足りない ── B を採る理由の 1 つがこれ
- NVMe 1 台の数字。SD カード・ネットワークドライブ・HDD では A の側だけが遅くなる
  ので、差は**さらに開く**（B の読む量は変わらない）
- Windows では測っていない

## 設計

### 1. ★の出所は `list_images`。あわせて `list_images` を並列化する

`ImageEntry` に `rating: Option<u8>` を足し、`list_images` が返す。
**同時に `direct_files` のループを `par_iter` にする。**

並列化は★を足すための道具であって、ついでの最適化ではない。逐次のままだと
1,000 枚で 576 → 650ms の悪化になり、`list_images` が返るまでグリッドは空なので
**フォルダーを開いた瞬間の停止時間がそのまま伸びる**。並列化すれば 169ms で、
現行（576ms）より速くなる。

- **並列化は順序を変えない。** `&Vec<T>` の `par_iter()` は `IndexedParallelIterator`
  で、`map` は indexed 性を保ち、`Vec` への `collect` は index どおりに詰める
  （順序が崩れるのは `for_each` ＋ 共有バッファのような unindexed な形）
- **ただし同値の順序は現行でも壊れている。** `entries.sort_by_key(|a| a.name.to_lowercase())`
  は安定ソートなので、同じ小文字名を持つ `A.jpg` と `a.jpg` の相対順は
  `direct_files` の順 ＝ **`read_dir` が返すファイルシステム順**のままになる。
  これは今日すでに実行ごとに変わりうる。比較を「小文字化した名前 → 元の名前」の
  2 段にして決定的にする（Phase 1 が `sortImages` で同値を名前の昇順に固定したのと
  同じ理由）。**並列化が持ち込む問題ではなく、並列化のついでに直す既存の欠陥である**
  ── 検査は並列化の前に落ちることを確認できる
- 逐次だったことに設計上の理由は無い（コメントも無く、`1bfb4f9` の信頼境界の整備を
  通しても素通りしている）。`read_image_ratings` は明示的に rayon を使っており、
  `spawn_blocking` の中で rayon を回す前例もそこにある

**消えるもの / 直すもの**:

| 対象 | 場所 |
|---|---|
| `read_image_ratings` コマンド（`MAX_BATCH = 64`） | `gui/src/commands.rs` |
| `RatingEntry` 型 | `gui/src/types.rs`（DTO 契約も再生成） |
| ★の保持ストア全体（`CHUNK`・`inFlight`・台帳） | `gui-frontend/src/lib/browser/ratings.svelte.ts` |
| 可視範囲が動くたびに★を要求する `$effect`（`mode !== "metadata"` のガードごと） | `gui-frontend/src/App.svelte:170` |
| `read_image_ratings` の同時呼び出しについての節 | `gui/src/security.rs` のモジュールコメント |
| **「★や撮影日で絞り込むにはフォルダー全体のメタデータ走査が必要で、それは別の設計になる」** | `gui-frontend/src/lib/browser/gridFilter.ts` のモジュールコメント（**この spec が嘘にする**） |
| **「可視範囲だけ読む。3,000 枚を先読みすると…」の理由づけ** | `ratings.svelte.ts` ごと消える |

**信頼境界は増えず、減る。** 新しいコマンドを足さないので webview から届く入力は
`list_images(path)` のまま（`security::existing_dir` を通る）。`MAX_BATCH` は
「パスの配列を受ける」ことに由来する防御で、ディレクトリ 1 本を受ける
`list_images` には元々不要である。

#### 決定: ★は情報モードに入らなくても常時出す（**裁定 X1 の反転**）

現行は `App.svelte:170` の `if (mode !== "metadata") return;` により、
**変換モードでは★を 1 枚も読まない**。`metadata.spec.ts:427` の
「情報モードへ入っただけで、読み込み時点の★がタイルに出る（**裁定 X1**）」は
その前提の上に立っており、`metadata.spec.ts:441` は
「フォルダーを開いた直後は★が出ていない」を前提条件として assert している。

★を `list_images` に畳むと、**この前提は成り立たなくなる。**
★はフォルダーを開いた瞬間からタイルに出る。

**それを許容する。** 理由:

- ★は「どれを変換するか」を選ぶための情報でもある。変換モードで見えない方が不自然
- 裁定 X1 が守っていたのは「保存を経由せずに★が出ること」であり、それは
  **より強い形で満たされる**（モード切替すら要らない）。X1 が防ぎたかった
  「可視範囲起点の `$effect` を消しても保存経由のテストだけでは気づけない」という
  検出力の穴は、★の経路が `list_images` 1 本になることで構造的に消える
- 並列化により、変換モードだけの利用者も現行より速くなる（576 → 169ms）。
  R-09 が問題にした「変換モードだけの利用者は、いまゼロのコストを払うことになる」は、
  並列化とセットにしたことで成立しない。**セットで入れることがこの設計の条件である**

**壊れる既存テスト**（テスト方針にも再掲）:

| テスト | 何が起きるか |
|---|---|
| `metadata.spec.ts:427` 裁定 X1 | `:441` の前提条件 assert が落ちる。テストの主張自体が意味を失うので**書き換える**（「フォルダーを開いた瞬間に★が出る」へ） |
| `metadata.spec.ts:404` 保存した★がタイルに出る | `:407` の「いまは★が出ていない」は、スタブがその写真に★を仕込まない限り通る。前提条件のコメントを実態に合わせる |
| `gridFilter.spec.ts` の `tileNames()` 完全一致（`:63,68,78,86`） | `tileLabel()`（`gridMetrics.ts:148`）が★を aria-label に連結するので、スタブに★を入れると `"photo-0000.jpg ★3"` になり全部落ちる。**期待値に★を含める**か、名前だけを取り出す |

#### 決定: `list_images` は `warnings` を捨てる

`read_metadata_bytes` は `warnings` を積む（「Exif を解析できませんでした」など）。
CLAUDE.md の不変条件は「出すか捨てるかは境界が決める」。**ここでは捨てる。**

- 3,000 枚ぶんの警告は利用者に見せる形が無く、`ImageEntry` にも戻り値にも置き場が無い
- 同じ写真を情報モードで開けば、`read_image_metadata` が同じ警告を 1 枚分だけ返す。
  **情報が失われるのではなく、出す場所が 1 箇所に寄る**
- `list_images` の戻り値の形は変えない（DTO 契約の変更は `ImageEntry.rating` の追加と
  `RatingEntry` の削除だけに留まる）

### 2. core の軽量読み取り経路。**読む側は 1 つの入口を通す**

```rust
/// JPEG の先頭（SOI〜SOS）だけから、人が編集する 3 項目を読む。
pub fn read_metadata_header(path: &Path) -> Result<MetadataRead>
```

SOI から順にセグメントを辿り、**APP1 だけを写した最小の JPEG**
（SOI ＋ APP1 群 ＋ SOS ヘッダ ＋ EOI）を組み立てて、既存の解析に渡す。

- **解析の実装は一切変えない。** `read_metadata(path)` を
  「ファイル全体を読む」＋ `read_metadata_bytes(raw, path)` に割る作業は
  **`d90a830` で済んでいる**（`core/src/metadata/mod.rs:150-162`）。
  `read_metadata_header` は同じ `read_metadata_bytes` を呼ぶ。
  Exif と XMP の優先順位・警告・trim 規則は
  [メタデータ編集 spec](2026-08-18-metadata-editing-design.md) のまま
- APP1 以外（APP0 JFIF / APP2 ICC / APP13 IPTC / DQT / DHT / SOF / APP14）は
  `seek_relative` で飛ばす。`Seek::seek` を使わない（前述の罠 3）
- 実装の下敷きは spike の `header_jpeg`（`rating_scan_spike.rs:45`）

**前方 N バイト一括（B'）は採らない。** 実測で B と差が無く（68 vs 79ms）、
正当化できない定数 `PREFIX` を抱えることになる。`PREFIX` を決めるには
「機種ごとに SOI〜SOS がどれくらいか」の分布が要るが、それは測れていない。
B は分布に依存しない（APP1 を全部写し、SOS まで辿るだけ）。

#### 決定: 入口を `read_metadata_fast` 1 つにし、読む側は全部そこを通す

```rust
/// 読み取りの唯一の入口。**★を読むところは全部これを使う。**
pub fn read_metadata_fast(path: &Path) -> Result<MetadataRead>
```

| 段 | 動き |
|---|---|
| 1 | 拡張子が JPEG でなければ `Ok`（全項目 `None`）で返す |
| 2 | `read_metadata_header` で先頭だけ読む。`Ok` ならそれを返す |
| 3 | `Err` なら `read_metadata`（全体読み）へ**フォールバック**する |

**呼び出し元は 3 つ。全部これを通す**（R-17）:

| 呼び出し元 | いま |
|---|---|
| `list_images`（グリッドの★） | 新規 |
| `read_image_metadata`（情報パネル） | `read_metadata` |
| **`write_image_metadata` の読み戻し**（`commands.rs:728`） | `read_metadata` |

3 つ目を外してはならない。**§5 が★の書き戻しの「値の出所」に指定しているのが
まさにこの応答**である。ここだけ経路が違うと「保存した直後だけ正しい★／
フォルダーを開き直すと違う★」という、**再現条件が「保存を挟んだかどうか」になる差**
が出る ── 1 本化が避けようとした事態そのものになる。

##### なぜフォールバックが要るか（R-19）

`read_metadata_header` は手書きのセグメント走査なので、「境界が 0xFF で始まっていない」
「セグメント長が短すぎる」で `Err` を返す。一方いまの `read_metadata` は
`img_parts` と `little_exif` にバイト列ごと渡すので、多少歪んでいても APP1 に
辿り着けば読める。**1 本化を素直にやると、いままで情報パネルで開けていた写真が
エラートーストになる**（タイトルもコメントも出せず、編集して保存する導線ごと塞がる）。

フォールバックすれば:

- **寛容さが今より下がらない。** 現行で読めていたものは読めたままである
- **食い違いは起きない。** 分岐しても値は一意（成功した側の値）で、
  3 つの呼び出し元は同じ `read_metadata_fast` を通る
- **性能は現行以上に悪くならない。** 歪んだファイルだけが現行と同じコストに戻る

なお **PNG / WebP はこの分岐に到達しない**。`security::readable_jpeg` が非 JPEG を弾き、
`App.svelte` の `editingIsJpeg` も守っている。段 1 の拡張子分岐が効くのは
`list_images` からの呼び出しだけである。

#### 非 JPEG は意図的に非対称にする

`list_images` は PNG / WebP も並べる（`is_supported_image` は `jpg|jpeg|png|webp`）。

| 経路 | PNG / WebP |
|---|---|
| `read_metadata` | **`Err`**（`Jpeg::from_bytes` が失敗 →「JPEG として読めません」） |
| `read_metadata_fast` | **`Ok` かつ全項目 `None`**（段 1 で返す） |

`read_metadata` との**一致は JPEG についてのみ主張する。** 非 JPEG を `Ok(None)` に
するのは、★の読み取りが**一覧表示の副作用**だからである ── PNG が混ざっている
だけで一覧が失敗したり警告が出たりしてはいけない。SOI 検査で弾く spike の
`header_jpeg` とは違い、**拡張子による分岐を入口に書く**（spike をそのまま
移植すると PNG で `Err` になる）。

JPEG については、フォールバックがあるので
**`read_metadata_fast` と `read_metadata` の結果は構成上つねに一致する**
（先頭経路が成功すれば同じ `read_metadata_bytes` に同じ APP1 を渡しており、
失敗すれば `read_metadata` そのものを呼ぶ）。壊れた JPEG は両方が `Err` になり、
`list_images` の側で `None` に落とす（一覧を失敗させない）。

この「つねに一致」は **APP1 が SOS より前にある**という、JPEG として一般的な
構成が前提である。SOS より後ろに APP1 を置いた非標準ファイルでは、先頭走査は
（APP1 を素通りしたまま）SOS に達して**成功**してしまい、フォールバックせずに
APP1 抜きの値を返す ── つまり `read_metadata` 側と食い違いうる。`img_parts` も
通常は SOS で走査を止めるため実害は考えにくいが、無条件の保証ではない。

### 3. 絞り込みの意味論

`gui-frontend/src/lib/browser/gridFilter.ts` に足す。**Phase 1 と同じく IPC を
一切しない純関数のまま**（`ImageEntry` に★が入っているので、その前提が保てる）。

```ts
export interface RatingFilter {
  /** ★の下限。**null は「★の付いた写真は出さない」** */
  min: 1 | 2 | 3 | 4 | 5 | null;
  /** 未評価（rating === null）も出すか */
  includeUnrated: boolean;
}
```

**`min: 1` が「★で絞り込んでいない」である。** ★は 1〜5 しか取らない
（★0 は書き込まず、他アプリが書いた `xmp:Rating = 0` も `read_metadata` が
`None` に落とす。`xmp.rs:80` の `parse_stars` と `mod.rs:98` の `percent_to_stars`）。
だから `min` に「絞り込まない」専用の値は要らず、`null` を「★ありは出さない」に使える。

#### UI は名前付きの 7 択にする（2 つのつまみを利用者に組み立てさせない）

内部表現は上の `RatingFilter` のままだが、**画面に出すのは 1 つの `<select>`**。

| 選択肢（画面） | `min` | `includeUnrated` |
|---|---|---|
| すべて（**既定**） | `1` | `true` |
| ★が付いているもの | `1` | `false` |
| ★2 以上 | `2` | `false` |
| ★3 以上 | `3` | `false` |
| ★4 以上 | `4` | `false` |
| ★5 | `5` | `false` |
| 未評価だけ | `null` | `true` |

**2 軸を画面に出さない理由**（R-06）:

- 2 軸のままだと「なし / ★1 / …」の「なし」が日常語で「★での絞り込みなし」と
  読めてしまう。実際の意味は「★ありを全部隠す」なので、**絞り込みを解除しようと
  した利用者の画面から★付きが全部消える**。初期値でだけ防いでも意味が無い
- 2 軸には「両方切った状態 = 常に 0 件」という意味のない組み合わせがある。
  7 択なら利用者が選べない
- 並び順が既に `<select>` なので、ヘッダーの言語が揃う
- ヘッダーの幅が足りる（設計 §6。★6 段＋トグルの 170px に対して 140px）

**捨てるもの**: `min: n` ＋ `includeUnrated: true`（「★n 以上 ＋ 未評価」＝
「★1〜n-1 だけを除く」）は 7 択から漏れる。内部表現には残るので、
要望が出たら選択肢を足すだけで足りる。

**この対応表は `gridFilter.ts` に置く**（`SORT_LABELS` / `DEFAULT_SORT` と同じ場所）。

```ts
export const RATING_PRESETS: { label: string; filter: RatingFilter }[] = [...];
```

`GridFilterBar` はこれを `<select>` に流し、テストは**同じ配列を回す**。
`GridFilterBar.svelte` の中に置くと、純関数のテストから参照できないので
「7 択それぞれを検査する」がラベルと値の手書きの写しになり、**写し間違えても
緑になる**（R-21）。CLAUDE.md が `gridFilter.ts` を「一覧の順序を決める規則」の
権威に置いているのとも揃う。

並べる順は `arrangeImages(images, query, rating, sort)` = 名前で絞る → ★で絞る →
並び替える。

### 4. 順序と index の不変条件（Phase 1 から変わらない）

**一覧の順序を決めるのは `gridFilter.ts` の 1 箇所だけ**で、`App.svelte` の
`visibleImages` が唯一の出所。サムネイル要求・情報モードの「次の写真」・変換対象が
この配列を index 参照するので、順序が 2 箇所で決まると index がずれ、そのまま
**別の写真を処理する**に化ける。★の絞り込みは `arrangeImages` の中に足すだけで、
この構造は変えない。

**絞り込みは表示だけを変える**（Phase 1 の規則をそのまま適用）:

- 選択は解除しない。隠れた選択は「N 枚選択中（M 枚は非表示）」と出す
- 変換対象からは減らさない。並び順だけ画面に合わせる
  （`selectedImages` は `images` を `sortImages` するだけで `filterImages` を通らない。
  ★の軸を足しても影響を受けない）

#### スクロールを先頭へ戻す条件に★を足す

`App.svelte:182` の `$effect` は依存を**明示列挙**している
（`searchQuery` / `gridSort.key` / `gridSort.desc`）。★の条件を足さないと、
下までスクロールした状態で「★4 以上」に絞っても先頭に戻らず、
**一覧が短くなったぶん `scrollTop` がクランプされて末尾が表示される。**

**依存は `visibleImages` ではなく絞り込み設定そのもの**（`ratingFilter.min` と
`ratingFilter.includeUnrated`）に張る。`visibleImages` に張ると、§5 の
「保存 → その場で書き換え → グリッドから消える」でもスクロールが飛ぶ
（§5 が `list_images` を呼び直さない理由がまさにそれである）。

### 5. 保存後の反映

情報モードで★を保存したら、`images` の該当 `ImageEntry.rating` を**その場で
書き換える**。`list_images` は呼び直さない ── スクロール位置と選択が飛ぶ。

#### 何を・いつ・失敗したらどうするか

| | 決めたこと |
|---|---|
| **値の出所** | **保存の応答**（`writeImageMetadata` の戻り＝**書いた後のファイルの実際の中身**）。`metadataDraft.save()` はそれを `values` に採っている（`metadataDraft.svelte.ts:93-94`）ので、保存成功後に `metadata.values.rating` を読む |
| **時点** | `handleSaveMetadata()` が `true` を返したときだけ。`save()` は「保存中に別の写真へ移った」でも `false` を返すので、その分岐に自然に乗る |
| **失敗時** | 書き換えない（`catch` は既に `if (didSave)` の外） |

**送信した下書きの値を採ってはならない。** Rust 側の正規化（空文字 → タグ削除、
★の範囲外 → `None`）と食い違い、**グリッドの★がディスクに無い値になる**。
`metadataDraft` は同じ罠を踏んで避けており（そのコメントが残っている）、
ここもそれを引き継ぐ。

#### 条件から外れた写真はグリッドから消える

「未評価だけ表示して★を付けていく」が「処理済みが消えていく」形で成立する。

- 「保存して次の写真へ」は既に**保存前に**次を確定している
  （`App.svelte:360` の `const next = nextImagePath;`）ので、送り先は失われない
- 編集対象は `editingPath` が持っており `visibleImages` に依存しないので、
  消えても情報パネルは開いたまま

#### 「保存」だけを押したら操作はそこで終わる（**仕様**）

**保存に成功すると両方のボタンが無効になる。これは絞り込みと無関係な現行の挙動である。**
`MetadataPanel.svelte:46` の

```js
let canSave = $derived(editable && canWrite && draft.isDirty && !draft.saving);
```

は `draft.isDirty` を含み、`metadataDraft.save()` は成功時に
`saved` と `values` の両方へ応答を代入する（`metadataDraft.svelte.ts:93-94`）ので、
保存直後は `isDirty` が `false` ＝ `canSave` が `false` になる。
「保存」も「保存して次の写真へ」も、**`hasNext` の値に関係なく**押せない。

したがって「絞り込み中に『保存』を押すと先へ進めない」は絞り込みが持ち込む欠陥ではなく、
保存ボタンの既存の振る舞いである。絞り込みはそこに「タイルがグリッドから消える」を
足すだけで、**行き止まりそのものは今日もある**。

**これを仕様とする。次はグリッドから選び直す。**

- 主用途の「未評価に★を付けて回る」は**「保存して次の写真へ」を押し続ける**導線で
  成立している（`App.svelte:360` が保存前に次を確定するため、消えても送り先は残る）
- 消えた写真を「次」に復元する仕組み（編集中の index を覚える等）は**作らない**。
  `canSave` が `false` である以上ボタンは押せないままで、**症状は 1 ミリも変わらない**
  一方、状態だけが 1 つ増える

> 改訂前の spec はここに「編集中の写真の index を覚え、消えたら同じ index の写真を
> 次とする」を書いていた。index の算術自体は正しいが（1 枚抜けた配列では抜けた位置に
> 元の「次」が詰まる）、**効く場面が無い**。`hasNext` ではなく `canSave` が
> ボタンを縛っていることを見落としていた（R-16）。

### 6. ヘッダーの段の作り方

**Phase 1 のヘッダーは最小幅で既に破綻している。** 実測（1100px 窓・右パネル開）:

- グリッドヘッダーの実効幅は **460px**（左のフォルダーツリーと右パネルが残りを取る）
- 「1 枚選択中」の `.selected` は max-content 58px に対して **12px**（縦書き 1 文字ずつ）。
  `white-space: nowrap` が付いているのは `.count` だけである
- 「並び順」と「サイズ」のラベルが重なり、検索欄の placeholder は「ファイ」で切れ、
  ヘッダーの高さが 97px（3 行分）になる

#### 実測値（max-content。**用語を 1 つに揃える**）

> **`.filters` は `GridFilterBar.svelte` のルート要素を指す**（検索 ＋ 並び順 ＋ 向き ＋ ★を
> 数えているのはこちら）。`GridHeader.svelte` 側の**グループ容器は別名にすること** ──
> 入れ子で同じクラス名にすると、Playwright の `page.locator(".filters")` が
> 2 つに一致して strict mode violation になり、レイアウト検査が実行できない。
> 実装計画は外側を `.filters-area` にしている。

| ブロック | max-content | 1100px/開 での実幅 |
|---|---|---|
| `.count`（枚数） | 29px | 29px |
| `.selected`（N 枚選択中） | 58px | **12px** |
| 全解除ボタン | 67px | 66px |
| `.filters`（検索 ＋ 並び順 ＋ 向き） | **360px** | **77px** |
| `.controls`（サイズ） | 140px | 140px |
| `primaryAction`（右パネルを畳んだときだけ） | 117px | — |
| 開閉ハンドル | 40px | 40px |

`.filters` の 360px は「検索 200（`max-width`）＋ 並び順 104 ＋ 向き 40 ＋ gap」。
**min-content は 232px**（検索が `min-width: 72px` まで縮んだとき）。
改訂前の spec はこの 232 を「自然幅」と書いており、**min-content と max-content を
混ぜていた**（R-13）。以降 max-content で統一する。

#### `flex-wrap: wrap` 単独では出せない（R-02）

`.grid-header` の flex アイテムはソース順に
**count → selected → 全解除 → filters → spacer → controls → primary → handle**。
`flex-wrap` はソース順にしか折り返せないので、「1 段目 = 枚数群 ＋ サイズ ＋ ハンドル /
2 段目 = 検索群」という並びは**絶対に出ない**。

実測（各ブロックに max-content の `min-width` を与えて `flex-wrap: wrap` を当てた）:
**ヘッダーの高さは 179px**（現行の破綻した 97px よりさらに高い）。改訂前の
「折り返せば 2 段とも収まる」という分析は成立しない。

#### 3 つのグループに分け、`grid-template-areas` で段を明示する

```
.status   枚数 / N 枚選択中 / 全解除
.filters  検索 / 並び順 / 向き / ★
.tools    サイズ / 主アクション / 開閉ハンドル
```

| 幅 | `grid-template-areas` |
|---|---|
| 広い | `"status filters tools"`（列は `auto 1fr auto`） |
| 狭い | `"status tools" "filters filters"`（列は `1fr auto`） |

切り替えは**ヘッダー自身の幅**で決まる（窓幅ではない ── 左右のパネルは
利用者がドラッグで変えられる）ので、親に `container-type: inline-size` を置いた
**コンテナクエリ**で切る。`@media` では正しく切れない。

#### 段の内訳（★の `<select>` を 140px と見積もった場合）

**gap のトークンを取り違えない**（R-18）。`.filters`（`GridFilterBar.svelte:65`）は
`var(--space-2)` = **8px**、`.grid-header`（`GridHeader.svelte:92`）は
`var(--space-3)` = **12px** である。改訂前の表は `.filters` の内部にも 12px を使い、
`.status` / `.tools` の内部 gap を丸ごと落としていた。

**決定**: `.status` / `.tools` の内部 gap と、3 グループのあいだの gap は
どちらも `--space-3`（12px）── いまのヘッダーの間隔をそのまま保つ。
`.filters` の内部は `--space-2`（8px）のまま。

| グループ | 内訳 | 幅 |
|---|---|---|
| `.status` | 枚数 29 ＋ 選択中 58 ＋ 全解除 67 ＋ gap 12×2 | **178px** |
| `.filters`（max-content） | 検索 200 ＋ 並び順 104 ＋ 向き 40 ＋ ★ *140* ＋ gap 8×3 | **508px** |
| `.filters`（min-content） | 検索 72 のとき | **380px** |
| `.tools` | サイズ 140 ＋ ハンドル 40 ＋ gap 12 | **192px** |
| `.tools`（右パネル畳。`primaryAction` 込み） | 140 ＋ 117 ＋ 40 ＋ gap 12×2 | **321px** |

| 形 | 内訳 | 合計 |
|---|---|---|
| 1 段（広い） | status 178 ＋ filters 508 ＋ tools 192 ＋ gap 12×2 ＋ padding 24 | **926px** |
| 2 段・1 段目 | status 178 ＋ tools 192 ＋ gap 12 ＋ padding 24 | 406px |

| 2 段・1 段目（右パネル畳） | status 178 ＋ tools 321 ＋ gap 12 ＋ padding 24 | 535px |

- **1100px / 右パネル開（460px）**: 2 段。1 段目 406 ✓ / 2 段目 404 ✓。
  検索欄は 200 → 128px に縮む（`min-width: 72px` の上）
- **1100px / 右パネル畳（780px）**: 2 段。1 段目 535 ✓ / 2 段目 404〜508 ✓
- **1600px / 開（960px）**: 1 段（926 ≤ 960）。**余裕は 34px しかない**
- 切り替えの閾値は **930px** 前後

#### あわせて直す

- `.selected` に `white-space: nowrap` を入れる。**入れないと縦書きの破綻が
  `scrollWidth` に現れず、テストで検知できない**（R-03 と対になる）
- 2 段になったときのヘッダー高さは約 2 行分。現行の破綻した 97px と同程度で、
  グリッドの表示領域は減らない

> **★の `<select>` の 140px は見積もりである。** 部品ができたら最小幅で実測し、
> 入らなければ選択肢のラベルを詰める（「★が付いているもの」→「★あり」）。
> 見積もりのまま次の工程へ渡さない。

## テスト方針

### レイアウトの検査を作り直す（**先に落ちることを確認してから直す**）

`gridFilter.spec.ts` の「最小ウィンドウ幅でもヘッダーが横に溢れない」は
`scrollWidth <= clientWidth` を見ている。**これは flex が縮んだだけでも成立する**ので、
現行の破綻を検知できていない（実際に通っている）。

**`scrollWidth` に置き換えるだけでは足りない**（R-03）。`.selected` はテキストが
縦に折り返しているだけで**溢れてはいない**ので、`scrollWidth === clientWidth` が
成立する。改訂前の spec は自分が指摘した罠を置き換え先で踏んでいた。

検査は次の 3 つを組む:

1. **max-content 幅**（クローンに `width: max-content` を当てて測る）を各グループの
   実幅と比べ、下回っていないこと
2. **各グループが 1 行に収まっていること**（`clientHeight` が 1 行分以下）。
   `.selected` の縦書きはここで落ちる
3. **スクリーンショットを撮って目で見る**。上の破綻は px を並べた時点では
   「77px、まあ狭い」に見え、画像を見て初めて縦書きとラベル重なりが分かった

段の切り替えは広い側（1600px）と狭い側（1100px）の両方で検査する。

### 純関数（`gridFilter.test.ts`）

- **7 択それぞれ**が期待どおりの集合を返すこと（設計 §3 の対応表がそのまま期待値）
- 閾値の境界（「★3 以上」で★3 が出て★2 が出ない）
- `rating === null`（未評価）の扱い。`rating === 0` はここに来ない
  （`read_metadata` が `None` に落とす。根拠は `xmp.rs:620` の既存テスト）
- 検索との合成（名前で落ちた写真は★の条件を満たしても出ない）
- 「未評価だけ」で 0 件になる場合がエラーにならないこと
- **否定形の検査には前提条件の assert を添える**（「隠れていないから 0」でも
  緑になるのを防ぐ）
- `arrangeImages` の引数が増えるので、`gridFilter.test.ts` の `describe("arrangeImages")` の
  呼び出しを直す（既存は 1 箇所）

### e2e（`gridFilter.spec.ts`）

- 7 択で絞られ、ヘッダーが「N / M 枚」になる
- 「未評価だけ」が効く
- 絞り込み中に「**保存して次の写真へ**」を押すと、その写真はグリッドから消え、
  **パネルは次の写真へ送られている**（保存前に次を確定しているため）
- 「保存」だけを押した場合は、写真が消えて**両方のボタンが無効になる**（設計 §5）。
  「次へが有効であること」を検査してはならない ── `canSave` が `false` なので
  **必ず落ちる**（R-16）。検査するのは「消えること」と「無効になること」である
- どちらの検査も `canSave` を満たす前提が要る（承認済み ＋ 変更あり）。
  既存の「情報モードの『次へ』は絞り込みの中だけを進む」が
  「このフォルダーへの書き込みを許可」と `fill(...)` を先に実行しているのと同じ形
- ★の条件を変えるとスクロールが先頭へ戻る（R-05）
- 隠れた選択が変換対象から減らない（Phase 1 の規則が★でも守られる）

スタブ（`e2e/stub.ts`）の `list_images` に★を持たせる。★あり・なしを混ぜ、
**名前順とも更新日順とも一致しない並び**にする。

**★を入れると既存の期待値が落ちる**（設計 §1 の表）。落ちるものを先に直す:

- `metadata.spec.ts:427`（裁定 X1）を「フォルダーを開いた瞬間に★が出る」へ書き換える
- `metadata.spec.ts:404` の前提条件コメントを実態に合わせる
- `gridFilter.spec.ts` の `tileNames()` 完全一致 4 箇所を、★込みの期待値にするか
  名前だけを取り出す形にする（`tileLabel()` は★を aria-label に連結する）

### Rust

- **`read_metadata_fast` が `read_metadata` と同じ★を返す（JPEG のみ）**。
  `core/tests/fixtures/exif-only.jpg`（Exif のみ）と `lightroom-xmp.jpg`（XMP 付き）
- **フォールバックが効くこと**（R-19）: `read_metadata_header` が `Err` になる歪んだ
  JPEG で、`read_metadata_fast` は `read_metadata` と同じ結果を返す。
  **前提条件として `read_metadata_header` 単体が `Err` になることを先に assert する**
  ── 入力が実は歪んでいなければ、フォールバックを消しても緑のままになる
- 非 JPEG は**意図的に非対称**（`read_metadata` は `Err`、`read_metadata_fast` は
  `Ok(None)`）。その非対称そのものを検査する
- APP1 を持たない JPEG で `Ok` かつ `None`
- 先頭も全体も読めないファイル（JPEG ですらないのに拡張子が `.jpg`）で `Err`。panic しない
- `list_images` が★の読み取り失敗で一覧ごと失敗しない
- `list_images` の並列化後も、同じ小文字名を持つ 2 ファイル（`A.jpg` / `a.jpg`）の
  順序が実行のたびに変わらないこと

**fixture は増やさず、バイト列をテスト内で組み立てる**（R-14）。
「APP1 の無い JPEG」「SOS が現れないファイル」「PNG のヘッダ」はどれも数十バイトで
書けるうえ、**何が入っていて何が入っていないかがテストの中で読める**。
`core/src/metadata/mod.rs` の既存のインラインテストがその形をとっており、
`core/tests/` の統合テストからは `core/src/lib.rs` の `#[cfg(test)]` ヘルパが
使えないという事情もある。実ファイルが要るのは既存の 2 fixture だけ。

## 未検証（実装時に必ず潰すこと）

1. **★の `<select>` の実幅**（設計 §6）。140px は見積もりで、段の切り替え閾値
   （約 930px）もそこから出ている。部品ができたら最小幅で測る。
   **1600px / 右パネル開（実効 960px）の余裕は 34px しかない**ので、
   **★が 175px を超えると 1600px の窓でも 2 段になる** ── 「広い画面では 1 行」という
   §6 の約束が静かに崩れるので、超えたらラベルを詰める
   （「★が付いているもの」→「★あり」）
2. **コンテナクエリが WebKitGTK で効くこと**（設計 §6）。効かない場合の代替は
   「`.filters` を常に 2 段目に置く」（幅に関係なく 2 段。約 44px を常に失うが
   機構は要らない）。**どちらを採ったかを実施メモに残す**
3. **機種ごとの SOI〜SOS の大きさ**。実測は 1 機種 26.8KB のみ。大きな MakerNote や
   Extended XMP を持つファイルで B が正しく・速く動くか。
   **正しさはフォールバックが担保する**（読めなければ全体読みへ落ちる）ので、
   ここで確かめたいのは「フォールバックへ落ちる頻度が実用上ゼロか」である ──
   常時落ちるなら軽量経路の意味が無い
4. **`list_images` の並列化が実機で効くこと**。実測は spike の合成コーパスで、
   `list_images` そのものを並列化して測ったわけではない。5,000 枚で
   グリッドが出るまでの体感を確認する
5. **Windows での挙動**。`seek_relative` の効きとページキャッシュの振る舞い
6. **DTO 契約の再生成**（`UPDATE_DTO_CONTRACT=1 cargo test -p picture-tool-gui contract`）。
   `ImageEntry` にフィールドを足し `RatingEntry` を消すので、忘れると
   Rust ⇄ TS の食い違いが型検査を素通りする
