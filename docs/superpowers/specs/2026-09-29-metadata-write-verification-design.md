# メタデータ書き込みの検証強化 設計

**日付**: 2026-09-29
**対象**: `core/src/metadata/atomic.rs` の `verify`（書き込み後・置き換え前の検証）と、
その結果を利用者へ届ける経路（`core::metadata::write_metadata` の戻り値、`gui/src/commands.rs` の境界）
**前提 spec**: [2026-08-18-metadata-editing-design.md](2026-08-18-metadata-editing-design.md)
（書き込むタグの仕様・信頼境界・原子的置換はそちらが正。本 spec は検証の中身だけを持つ）

## 背景と目的

メタデータ編集 spec は「既存 Exif を壊しうる書き込みは**壊さずに失敗する**」と主張しているが、
同 spec の「この保証の実際の強度」の節（ブランチ最終レビュー I-3）で、コードの保証がそれより
狭いことが記録された。

- `atomic::verify` の 3 番目の検査は、書き込み前後の `ExifInfo`（撮影情報 9 項目）しか比べていない
- したがって `little_exif` が**解析には成功するが書き戻しで一部を落とす**経路では、GPS・
  MakerNote・IFD1 サムネイル・ICC が消えても 9 項目が一致していれば置き換えまで進む
- 同節は「ゲートの強化は次のブランチの仕事」としている。本 spec がその仕事

**目的**: 本ツールが編集する 5 タグ以外のメタデータが書き込みで**消えた・変わった**ときに、
元写真を置き換えずに保存を失敗させる。失敗の文面で何が変わったかを示す。

現行の GUI 境界（`gui/src/commands.rs:765`）は `e.to_string()` で最上位の文脈（「メタデータを
保存できませんでした…」）しか webview へ渡さないので、内側の文面は利用者に届いていない。
**境界の文字列化の修正も本 spec に含める**（利用者判断 2026-09-30、UX 優先。レビュー F1 / Q4）。

## スコープ

### やること

- `verify` の 3 番目の検査（`ExifInfo` 比較）を、次の 3 つの検査で**置き換える**
  1. Exif 全フィールドの保全（編集対象と、位置に依存するだけの値を除く）
  2. IFD1 サムネイル本体のバイト列一致
  3. Exif・XMP 以外のセグメントのバイト列一致（相対順序を含む）
- 書き込み前の Exif を検証側の実装（kamadak-exif）で読めないときは保存を拒否する
- 現行の検査を前提に書かれたテストとコメントを追従させる（下記「テスト」と、
  `atomic.rs` 冒頭のモジュールコメント「既存 Exif が壊れていないか」、`mod.rs` の `build` 内の
  「`read_exif_info` は…`atomic::verify` を素通りする」の説明）
- MakerNote の位置が変わったときは保存を**通したうえで警告を返す**（下記「MakerNote の位置の変化」）
- GUI の境界で、保存失敗のエラーを文脈のチェーン全体（`format!("{e:#}")`）で文字列化する。
  既存の拒否の文面（「画素データが変化した」等）も、これで初めて利用者に届く
- メタデータ編集 spec の「この保証の実際の強度」の節を、強化後の実態に書き換える

### やらないこと

- **MakerNote の内部整合の検証。** MakerNote はメーカー独自形式で、内部に TIFF 先頭からの
  オフセットを持つものがある。本 spec の検査は MakerNote の**バイト列が変わっていないこと**
  までを保証し、**位置の変化は警告として知らせるに留める**（設計の「MakerNote の位置の変化」）。
  中のオフセットが実際に壊れたかどうかはメーカー形式ごとの解釈が要るので判定しない
- **XMP の保全の強化。** XMP は `xmp::patch` が 4 プロパティだけ差し替える設計で、多言語
  （Lang Alt）の畳み込み・Extended XMP の整合はメタデータ編集 spec の既知の制約のまま。
  ただし XMP APP1 が 2 つ以上ある JPEG で 2 つ目以降が消えることは、検査 3 が検知して拒否する
- **セグメントの配置の是正。** 実測で、書き込み後の Exif APP1・XMP APP1 が JFIF APP0 より前に
  来ることが分かった（下記「実測」）。JFIF 仕様上は APP0 が SOI の直後であるべきだが、
  既存の挙動であり本 spec の目的（消失の検知）とは別の問題として扱う
- `little_exif` の置き換え、Exif の自前書き込み（検討して不採用。下記「検討した案」）
- 実測用テスト `core/tests/metadata_spike.rs` の書き換え。本番実装から独立させておく価値が
  あるという同ファイルの方針どおり、触らない

## 実測（2026-09-29）

`write_metadata` でタイトル・コメント・★を書き、書き込み前後を kamadak-exif と `img-parts` で
比べた。
> **比較方法の注記（レビュー Q3）**: この実測は `Value` の `Debug` 表現で比べた。本 spec の比較規則
> （検査 1「値の比較規則」）そのものでの確認ではないので、**実装計画の最初のタスクで、実装した
> 比較規則を使って同じ 3 枚を再実測する**（利用者判断 2026-09-30）。
> **再実測（2026-09-30、実装計画 Task 1）**: 比較規則で読み直しても結果は同じだった（`JPEGInterchangeFormat` だけが変わり、`Undefined` の 3 項目は一致）。詳細は計画の実施メモ。
対象はフィクスチャ `exif-only.jpg`・`lightroom-xmp.jpg` と、実写真
（Lightroom Classic 15.2.1 書き出し、ILCE-7CM2、APP13 と ICC を持つ）の 3 枚。
3 枚とも結果は同じだった。

| 観測 | 内容 | 本 spec への帰結 |
|---|---|---|
| 消えたフィールド | 0 件 | 現行の `little_exif` はこの 3 枚を壊していない。新しい検査で**誤拒否しない**根拠 |
| 値が変わったフィールド | `In(1)/JPEGInterchangeFormat` のみ（1030 → 1180） | IFD0 が伸びた分だけサムネイルが後ろへ動く、定義上正しい変化。比較から除外する |
| `Debug` 表現だけ変わったフィールド | `ExifVersion`・`FileSource`・`SceneType`（`Value::Undefined` の `ofs`） | kamadak-exif の `Value::Undefined(bytes, ofs)` は **Exif 内の位置を値に含む**。比較は `ofs` を無視してバイト列で行う |
| 増えたフィールド | `0x4749`（RatingPercent）・`0x9c9b`（XPTitle）・`0x9c9c`（XPComment）・`UserComment` | すべて編集対象。増えることは許す |
| IFD ポインタ系のタグ | kamadak-exif は `ExifIFDPointer` 等を**フィールドとして返さない** | 除外リストに入れる必要がない |
| 型の正規化（撮って出し。実装後の最終レビューで追加） | Pixel 7 の撮って出し JPEG では `PixelXDimension`・`PixelYDimension` が SHORT → LONG（値は同じ）。上の 3 枚はもともと LONG なので現れなかった | 値の比較規則に、SHORT と LONG の両方を認めるタグに限った拡幅の例外を置く |
| セグメント | Exif・XMP 以外（JFIF APP0・APP13・ICC APP2・DQT 等）は内容も相対順序も不変。Exif APP1 と XMP APP1 が先頭へ移動 | 検査 3 は**絶対位置ではなく相対順序**で比べる |

## 設計

### 検査 1: Exif 全フィールドの保全

書き込み前（元写真）と書き込み後（一時ファイル）をそれぞれ kamadak-exif で読み（読み方は
「読めない場合の扱い」の節）、フィールドを `(ifd_num, tag)` をキーにした多重集合として比べる。
`tag` は kamadak-exif の `exif::Tag`（context と番号の組）である。

- **比較から除外するキー**（すべて `In::PRIMARY` に限る。IFD1 の同名タグは本ツールが書かないので除外しない）
  - 編集対象の 5 タグ: `Tag(Context::Tiff, 0x010e)`（ImageDescription）・`Tag(Context::Tiff, 0x9c9b)`
    （XPTitle）・`Tag(Context::Tiff, 0x9c9c)`（XPComment）・`Tag(Context::Tiff, 0x4749)`
    （RatingPercent）・`Tag(Context::Exif, 0x9286)`（UserComment）。kamadak-exif には XPTitle 等の
    名前付き定数が無いので番号で組み立てる。context を取り違えると除外が効かず全保存が拒否される。
    これらの**値の正しさ**は既存の 1 番目の検査（期待値どおりに読み戻せるか）が受け持つ
  - `In(1)/JPEGInterchangeFormat`（サムネイルへのオフセット）。サムネイルの保全は検査 2 が
    受け持つ。対になる `JPEGInterchangeFormatLength` は除外しない（長さの変化は切り詰めなので検知したい）
- **向き**: 除外キーを除いた多重集合について「書き込み前 ⊆ 書き込み後」を求める。つまり
  書き込み前にあった各フィールドが、書き込み後に**同じ値で**残っていること。
  書き込み後にだけあるフィールドは許す（`UserComment` を初めて書くと ExifIFD 側にエントリが
  増えるなど、増加はデータの消失ではない）。同じキーのフィールドが複数ある場合（壊れた IFD 等）も
  値の多重集合としてこの包含を求める
- **値の比較規則**: kamadak-exif 0.6 の `Value` は `PartialEq` を持たないので、次の規則で
  自前に比べる。`Debug` 文字列・`display_value()` の比較は使わない（前者は位置を含み、後者は
  表示用の整形で値の違いを丸めうる）
  - バリアントが違えば不一致（型の正規化、例えば SHORT → LONG の書き戻しも「変わった」とみなす）。
    **例外**: Exif／TIFF が SHORT と LONG の両方を認めるタグ（`ImageWidth`・`ImageLength`・`StripOffsets`・
    `RowsPerStrip`・`StripByteCounts`・`PixelXDimension`・`PixelYDimension`）に限り、書き込み前が `Short`、
    後が `Long` で要素列の値が同じなら一致とみなす（逆向きは不一致）。`little_exif` は既知のタグを自分の
    宣言した型で書き戻すため、SHORT で書かれた写真（Pixel 7 の撮って出しで実測）が保存のたびに拒否されるのを
    避ける（ブランチ最終レビュー C1、利用者判断 2026-09-30）。`ResolutionUnit` のような SHORT 限定のタグは拒否のまま
  - `Undefined(bytes, ofs)` はバイト列だけを比べ、`ofs` は無視する（上記の実測）
  - `Unknown(type, count, ofs)`（未知の型コード）は `(type, count)` だけを比べ、`ofs` は無視する。
    kamadak-exif は未知型の中身を返さないため、**中身の変化は検知できない**（残る制約として記録する）
  - `Float`／`Double` はビット列（`to_bits()`）で比べる（`NaN` が自分自身と不一致になる誤拒否を避ける）
  - `Rational`／`SRational` は分子・分母の組で比べる（約分しない）
  - それ以外（`Byte`・`Ascii`・`Short`・`Long`・`SByte`・`SShort`・`SLong`）は要素列で比べる

### 検査 2: IFD1 サムネイル本体のバイト列一致

書き込み前にサムネイル（`In(1)/JPEGInterchangeFormat` と `JPEGInterchangeFormatLength` が指す
範囲）があれば、書き込み後も同じバイト列のサムネイルがあることを求める。

- オフセットは**検査 1 で読んだのと同じ Exif APP1 セグメントの中身**（`Exif\0\0` の直後 = TIFF
  ヘッダ先頭）からの相対値として解決する。ファイル全体を `Exif\0\0` で検索する実測用テストの方法は、
  XMP 等の中に同じバイト列があると誤る可能性があるので本番では使わない
- 「サムネイルがある」とは、`JPEGInterchangeFormat` と `JPEGInterchangeFormatLength` の**両方**が
  あり、`offset + length` が `checked_add` で溢れず、TIFF 本体の範囲に収まること
- 書き込み前: 上の条件を満たさなければ（片方だけある・範囲外・溢れる）「元写真のサムネイルは
  壊れているか無い」として比較対象なし（何も求めない）
- 書き込み前にサムネイルがあった場合、書き込み後に上の条件を満たさないか、バイト列が違えば拒否する
- 範囲の計算で panic しないこと（panic は `catch_unwind` で捕まるが、文面が「異常終了しました」に化ける）

### 検査 3: Exif・XMP 以外のセグメントの一致

書き込み前後のそれぞれで、SOS より前のセグメントから **最初の Exif APP1（`Exif\0\0` で始まる APP1）と
最初の XMP APP1（`xmp::XMP_ID` = `http://ns.adobe.com/xap/1.0/\0` で始まる APP1）を除いた列**を作り、
マーカーと中身のバイト列が順序を含めて一致することを求める。

- 除外を「最初の 1 つ」に限るのは、検査 1・2 と kamadak-exif・`has_exif_segment`・`xmp::extract` が
  見るのが最初の 1 つだけだから。`little_exif` の `clear_segment` と `xmp::install` は前置きが一致する
  APP1 を**すべて**消すので、2 つ目以降を持つ JPEG（まれ）では 2 つ目以降の消失をここで検知して拒否する

- 本ツールはこれらのセグメントを触らないので、一致しなければ即異常
- ICC（APP2）・IPTC（APP13）・Extended XMP（`http://ns.adobe.com/xmp/extension/` の APP1）・
  JFIF APP0・量子化／ハフマン表がここで守られる
- 画素データ（SOS 以降）の一致は既存の検査（`replace_verified` 冒頭）が受け持つ

### MakerNote の位置の変化（警告）

検査 1 で `Tag::MakerNote`（`In::PRIMARY`）が前後に 1 つずつあり、バイト列が一致しているのに
`Value::Undefined` の `ofs`（TIFF 先頭からの位置）が違うときは、**保存を通したうえで警告を返す**
（利用者判断 2026-09-30。レビュー F3 / Q1）。

- **拒否しない理由**: IFD0 が伸びれば後方のデータは一律にずれるので、拒否にすると MakerNote 付きの
  写真（カメラ撮って出し JPEG 等）はほぼすべて保存できなくなる
- **警告の理由**: メーカーによっては MakerNote 内部のオフセットが TIFF 先頭基準で、位置がずれると
  レンズ情報などが他のソフトで正しく読めなくなりうる。保存は成功しても、利用者が気付ける状態にする
- **文面**: 「保存しました。ただしカメラ固有の情報（MakerNote）の位置が変わったため、他のソフトで
  一部の撮影情報が読めなくなる可能性があります」
- **経路**: `write_metadata` の戻り値を `Result<()>` から `Result<Vec<String>>`（警告の列）に変える。
  `core` は `eprintln!` しないという既存方針どおり、出すかどうかは境界が決める。GUI の
  `write_image_metadata` は、保存後に返す `MetadataRead` の `warnings` にこの警告を足す。
  `MetadataRead` の形は変わらないので Rust ⇄ TS の DTO 契約は変わらない。フロントエンドは保存後の
  `read.warnings` を既にメタデータパネルに表示している（`metadataDraft.svelte.ts` の保存処理）
- MakerNote のバイト列そのものが変わった・消えたときは検査 1 の拒否になる（警告ではない）

### 読めない場合の扱い

**Exif の有無と読み方**は、書き込み前後とも次の 1 つの規則に揃える。

- 有無の判定は `has_exif_segment`（`mod.rs`）と同じ規則: SOS より前の **最初の** `Exif\0\0` で始まる APP1
- 読むのはそのセグメントの中身の `Exif\0\0` より後ろ（TIFF 本体）を `exif::Reader::read_raw` に
  渡したもの。`read_from_container` は使わない（有無の判定が 2 系統に分かれ、食い違えば検査 1・2 が
  空振りで通るため）。検査 2 のオフセットの基準もこれと同じ
- `continue_on_error` は既定の `false` のまま使い、`Err` はすべて「読めない」とする。1 エントリでも
  壊れていれば拒否される（利用者判断 2026-09-30。レビュー F2 / Q2）。`true` にして部分結果を許すと、
  壊れたエントリが前後とも比較の外に落ち、「比べる基準が取れないのに通す」穴の縮小版になるため

| 書き込み前の状態 | 扱い |
|---|---|
| Exif APP1 が無い | 検査 1・2 は比べるものが無いので通す。検査 3 は行う |
| Exif APP1 があり、kamadak-exif で読める | 検査 1〜3 を行う |
| Exif APP1 があり、kamadak-exif で読めない | **保存を拒否する** |
| 書き込み後の Exif を kamadak-exif で読めない（書き込み前にあった場合） | 保存を拒否する |

3 行目は利用者判断（2026-09-29）。比べる基準が取れない以上、消えたかどうかを判定できない。
現行では、元の Exif を kamadak-exif が読めない場合 `read_exif_info` が `ExifInfo::default()` を返す。
書き込み後は読めて撮影情報が出れば前後が食い違って拒否されるが、**書き込み後も読めない（か
9 項目がすべて空の）場合は前後とも空で一致して素通りする**。この素通りがメタデータ編集 spec の
問題視した穴なので、`read_exif_info` は検証に使わない。

### エラー文面

既存の文面と同じく「何が起きたか」を示し、元写真が無事であることは `write_metadata` の
外側の文脈（「元ファイルは変更していません」）が伝える。

- 検査 1: 「既存の Exif が保存で失われるか変わるため中止しました: `<キー1>`, `<キー2>`, `<キー3>` ほか N 件」
  - 消えたものと値が変わったものを区別せず、1 つの文面にまとめる（利用者にとって「保存すると
    写真の情報が損なわれる」という意味は同じ）
  - キーは書き込み前の多重集合で包含が崩れたものを、`(ifd_num, tag 番号)` 順に最大 3 件並べる。
    4 件目以降があるときだけ「ほか N 件」を付ける
  - キーの表記: kamadak-exif が名前を知るタグはその名前（例 `GPSLatitude`）、知らないタグは
    `0x9c9b` のような 16 進の番号。IFD1（サムネイル側）のタグには「（サムネイル）」を後置する。
    kamadak-exif の `Tag` の `Display` は名前を知らないタグで `Tag(Tiff, 18249)` に落ちるので、
    そのまま使わない
- 検査 2: 「Exif のサムネイルが保存で変わるため中止しました」
- 検査 3: 「Exif・XMP 以外のメタデータ（`<名前>`）が保存で変わるため中止しました」
  - 名指すのは、前後の列を先頭から比べて最初に食い違った位置のセグメント（書き込み前の列の側。
    書き込み前の列が先に尽きたら書き込み後の列の側）
  - `<名前>` の対応表:

    | セグメント | 表記 |
    |---|---|
    | APP2 で `ICC_PROFILE\0` 始まり | ICC プロファイル |
    | APP13 で `Photoshop 3.0\0` 始まり | IPTC（Photoshop） |
    | APP1 で `http://ns.adobe.com/xmp/extension/\0` 始まり | 拡張 XMP |
    | APP1 で `Exif\0\0` 始まり（2 つ目以降） | 2 つ目の Exif |
    | APP1 で `XMP_ID` 始まり（2 つ目以降） | 2 つ目の XMP |
    | APP0 で `JFIF\0` 始まり | JFIF |
    | その他の APPn | `APPn` |
    | APP 以外（DQT・DHT・SOF 等） | 画像の符号化情報 |
- 読めない場合: 「既存の Exif を検証できないため中止しました」
- **利用者に届く形**: GUI の境界は `format!("{e:#}")` で文字列化するので、利用者に見えるのは
  「メタデータを保存できませんでした（元ファイルは変更していません）: `<パス>`: `<上の文面>`」の形になる
  （`anyhow` の文脈チェーンを `: ` で連結したもの）。`core` 側の文面は、この連結の末尾に来ても
  意味が通るように書く

### 置き場所

- 比較処理は新しいモジュール `core/src/metadata/preserve.rs` に置く。入力は書き込み前後の
  **SOS より前のバイト列**で、ファイルには触らない（単体テストで前後を直接組み立てられるように
  するため。検査 1〜3 はどれも SOS より前しか見ないので、画素データを複製しない）
- `atomic::verify` は既存の 1・2 番目の検査の後に `preserve::check(original_head, written_head)` を呼ぶ。
  `original_head` は `replace_verified` が既に持つ元写真のバイト列の SOS より前、`written_head` は
  **一時ファイルをディスクから読み戻したバイト列**の SOS より前（メモリ上の `patched` ではなく、
  実際に rename されるものを見る）。一時ファイルの読み戻しは既存の 1 番目の検査（`read_metadata`）と
  合わせて 2 回になるが、写真 1 枚分の読み込みであり受け入れる
- kamadak-exif で読めないことによる拒否を `build` の段階へ前倒しする最適化はしない（レビュー F11）。
  判定の置き場所を `preserve` の 1 箇所に保つ方を優先する
- `read_exif_info` を使う現行の 3 番目の検査は削除する（検査 1 がその上位互換）
- `preserve::check` は拒否を `Err`、MakerNote の警告を `Ok(Vec<String>)` で返す。`verify` →
  `replace_verified` → `write_inner` → `write_metadata` はこの警告の列をそのまま上へ返す

## 検討した案

| 案 | 不採用の理由 |
|---|---|
| Exif APP1 のバイト列を直接照合する | タグ 1 つの追加で後方のデータが丸ごとずれ、照合のためにオフセットを付け直す処理を自前で書くことになる。フィールド単位の比較で目的は足りる |
| `little_exif` をやめ、IFD0 だけを自前で書き換える | 消失の原因そのものを断てるが、実質 Exif 書き込み器の自作で範囲を大きく超える |
| 増えたフィールドも拒否する | 編集対象を初めて書くときの正常な増加を拒否してしまう。増加はデータの消失ではない |
| 読めない場合は従来の 9 項目比較で保存を許す | 検証されない経路が残り、本 spec の目的に反する（利用者判断で不採用） |
| MakerNote の位置の変化を拒否する | MakerNote 付きの写真がほぼすべて保存できなくなる（利用者判断で警告に留める） |
| 壊れたエントリを飛ばした部分結果（`continue_on_error(true)`）で比べる | 壊れたエントリが比較の外に落ちる（利用者判断で厳格読み） |

## テスト

`preserve::check` に書き込み前後のバイト列を直接渡す単体テストを中心にする。
書き込み後のバイト列はフィクスチャのコピーから対象を消す・変えることで作る。
**各拒否ケースでは、対象が書き込み前に実在することを先に assert する**
（対象がもともと無いせいで通る偽の成功を防ぐ）。

| ケース | 期待 |
|---|---|
| 編集対象外のタグ（例: GPS 系、無ければ `Make`）が消えた | 拒否。文面にタグ名が出る |
| 編集対象外のタグの値が変わった | 拒否。文面にタグ名が出る |
| 編集対象外のタグの型だけが変わった（同じ数値を SHORT → LONG） | 拒否 |
| 失われたタグが 4 件以上 | 拒否。3 件列挙＋「ほか N 件」 |
| サムネイル本体が変わった／消えた | 拒否 |
| ICC（APP2）などのセグメントが消えた／中身が変わった | 拒否。文面に「ICC プロファイル」 |
| 2 つ目の Exif APP1／XMP APP1 が消えた | 拒否 |
| Exif APP1 はあるが kamadak-exif で読めない | 拒否 |
| 編集対象の 5 タグだけが変わった／増えた／消えた | 通す |
| `JPEGInterchangeFormat` だけが変わり、サムネイル本体は同じ | 通す |
| MakerNote のバイト列は同じで位置だけが変わった | 通す。MakerNote の警告を返す |
| MakerNote の位置が変わらない（MakerNote を持たない写真を含む） | 通す。警告は返さない |
| Exif の 1 エントリだけが壊れている（kamadak-exif の厳格読みで `Err`） | 拒否 |
| Exif をもともと持たない | 通す |

- **誤拒否しないこと**: 既存の結合テスト（`core/tests/metadata_integration.rs`。Lightroom 形式の
  フィクスチャへの書き込みを含む）がそのまま通ること。`a_file_whose_exif_cannot_be_parsed_is_refused_without_being_modified`
  はメタデータ編集の判断の前提なので残す
- **既存の単体テストの書き換え**: `atomic.rs` の `replace_verified_refuses_a_buffer_that_lost_the_existing_exif`
  は現行の 3 番目の検査の文面（「既存の Exif が壊れました」）を assert し、doc コメントも
  `read_exif_info` の突き合わせを前提にしている。空の `Metadata` で書き直した buffer は、kamadak-exif が
  読めれば検査 1 で、読めなければ「検証できない」で拒否されるので、**どちらの経路で拒否されるかを
  前提条件の assert で固定してから**、その経路の文面を assert する形に書き換える。意図（little_exif
  自身は読めるが中身を失った buffer を拒否する）は保つ
- **GUI の境界**: 保存の拒否で、内側の文面（例「既存の Exif が保存で失われるか変わるため」）が
  `write_image_metadata` のエラー文字列に含まれること。MakerNote の警告が、保存後に返す
  `MetadataRead.warnings` に含まれること
- **検査が効いていることの確認**: 実装後に検査 1〜3 を一時的に無効化し、対応する拒否テストが
  落ちることを実測する
- **実写真**: `docs/tmp/` の Lightroom 書き出し写真（APP13・ICC 付き）のコピーへ実際に保存を
  通し、拒否されないことを確認する
- **フィクスチャ**: 実測では `exif-only.jpg`・`lightroom-xmp.jpg` ともにサムネイル
  （`JPEGInterchangeFormat` あり）を持つが、**ICC（APP2）を持たない**。検査 3 の拒否ケースは
  テスト内でセグメントを足した入力を組み立てる（`img-parts` で APP2 を挿入）ことで作る。
  フィクスチャファイルの追加が要るかは実装計画で決める

## メタデータ編集 spec への反映

「この保証の実際の強度」の節（ブランチ最終レビュー I-3 の記録）を次の内容に書き換える。

- 検査が比べる範囲（本 spec の検査 1〜3）と、それでも検知しない範囲（MakerNote 内部の
  オフセット整合 ── 位置の変化は警告のみ、未知の型コードを持つタグの中身、XMP 内部の保全）
- 「ゲート自体の強化は次のブランチの仕事」の一文は、本 spec へのリンクに置き換える
