# メタデータ書き込みの検証強化 設計

**日付**: 2026-09-29
**対象**: `core/src/metadata/atomic.rs` の `verify`（書き込み後・置き換え前の検証）
**前提 spec**: [2026-08-18-metadata-editing-design.md](2026-08-18-metadata-editing-design.md)
（書き込むタグの仕様・信頼境界・原子的置換はそちらが正。本 spec は検証の中身だけを持つ）

## 背景と目的

メタデータ編集 spec は「既存 Exif を壊しうる書き込みは**壊さずに失敗する**」と主張しているが、
同 spec の「この保証の実際の強度」の節（ブランチ最終レビュー I-3）で、コードの保証がそれより
狭いことが記録された。

- `atomic::verify` の 3 番目の検査は、書き込み前後の `ExifInfo`（撮影情報 9 項目）しか比べていない
- したがって `little_exif` が**解析には成功するが書き戻しで一部を落とす**経路では、GPS・
  MakerNote・IFD1 サムネイル・ICC が消えても 9 項目が一致していれば置き換えまで進む
- 同節は「ゲートの強化は次のブランチの仕事」としている。本 spec がその仕事

**目的**: 本ツールが編集する 5 タグ以外のメタデータが書き込みで**消えた・変わった**ときに、
元写真を置き換えずに保存を失敗させる。失敗の文面で何が変わったかを示す。

## スコープ

### やること

- `verify` の 3 番目の検査（`ExifInfo` 比較）を、次の 3 つの検査で**置き換える**
  1. Exif 全フィールドの保全（編集対象と、位置に依存するだけの値を除く）
  2. IFD1 サムネイル本体のバイト列一致
  3. Exif・XMP 以外のセグメントのバイト列一致（相対順序を含む）
- 書き込み前の Exif を検証側の実装（kamadak-exif）で読めないときは保存を拒否する
- メタデータ編集 spec の「この保証の実際の強度」の節を、強化後の実態に書き換える

### やらないこと

- **MakerNote の内部整合の検証。** MakerNote はメーカー独自形式で、内部に TIFF 先頭からの
  オフセットを持つものがある。本 spec の検査は MakerNote の**バイト列が変わっていないこと**
  までを保証し、Exif 内での**位置がずれたことで中のオフセットが指す先が狂う**ことは検知しない。
  残リスクとして記録する（本ツールの編集対象は Lightroom 書き出しで、実測した 3 枚はいずれも
  MakerNote を持たない）
- **XMP の保全の強化。** XMP は `xmp::patch` が 4 プロパティだけ差し替える設計で、多言語
  （Lang Alt）の畳み込み・Extended XMP の整合はメタデータ編集 spec の既知の制約のまま
- **セグメントの配置の是正。** 実測で、書き込み後の Exif APP1・XMP APP1 が JFIF APP0 より前に
  来ることが分かった（下記「実測」）。JFIF 仕様上は APP0 が SOI の直後であるべきだが、
  既存の挙動であり本 spec の目的（消失の検知）とは別の問題として扱う
- `little_exif` の置き換え、Exif の自前書き込み（検討して不採用。下記「検討した案」）
- 実測用テスト `core/tests/metadata_spike.rs` の書き換え。本番実装から独立させておく価値が
  あるという同ファイルの方針どおり、触らない

## 実測（2026-09-29）

`write_metadata` でタイトル・コメント・★を書き、書き込み前後を kamadak-exif と `img-parts` で
比べた。対象はフィクスチャ `exif-only.jpg`・`lightroom-xmp.jpg` と、実写真
（Lightroom Classic 15.2.1 書き出し、ILCE-7CM2、APP13 と ICC を持つ）の 3 枚。
3 枚とも結果は同じだった。

| 観測 | 内容 | 本 spec への帰結 |
|---|---|---|
| 消えたフィールド | 0 件 | 現行の `little_exif` はこの 3 枚を壊していない。新しい検査で**誤拒否しない**根拠 |
| 値が変わったフィールド | `In(1)/JPEGInterchangeFormat` のみ（1030 → 1180） | IFD0 が伸びた分だけサムネイルが後ろへ動く、定義上正しい変化。比較から除外する |
| `Debug` 表現だけ変わったフィールド | `ExifVersion`・`FileSource`・`SceneType`（`Value::Undefined` の `ofs`） | kamadak-exif の `Value::Undefined(bytes, ofs)` は **Exif 内の位置を値に含む**。比較は `ofs` を無視してバイト列で行う |
| 増えたフィールド | `0x4749`（RatingPercent）・`0x9c9b`（XPTitle）・`0x9c9c`（XPComment）・`UserComment` | すべて編集対象。増えることは許す |
| IFD ポインタ系のタグ | kamadak-exif は `ExifIFDPointer` 等を**フィールドとして返さない** | 除外リストに入れる必要がない |
| セグメント | Exif・XMP 以外（JFIF APP0・APP13・ICC APP2・DQT 等）は内容も相対順序も不変。Exif APP1 と XMP APP1 が先頭へ移動 | 検査 3 は**絶対位置ではなく相対順序**で比べる |

## 設計

### 検査 1: Exif 全フィールドの保全

書き込み前（元写真）と書き込み後（一時ファイル）をそれぞれ kamadak-exif で読み、
フィールドを `(ifd_num, tag)` をキーにした集合として比べる。

- **比較から除外するキー**
  - 編集対象の 5 タグ: `ImageDescription`（0x010e）・`XPTitle`（0x9c9b）・`XPComment`（0x9c9c）・
    `RatingPercent`（0x4749）・`UserComment`（0x9286）。これらの**値の正しさ**は既存の
    1 番目の検査（期待値どおりに読み戻せるか）が受け持つ
  - `In(1)/JPEGInterchangeFormat`（サムネイルへのオフセット）。サムネイルの保全は検査 2 が
    受け持つ。対になる `JPEGInterchangeFormatLength` は除外しない（長さの変化は切り詰めなので検知したい）
- **向き**: 書き込み前にあった各フィールドが、書き込み後に**同じ値で**残っていることを求める。
  書き込み後にだけあるフィールドは許す（`UserComment` を初めて書くと ExifIFD 側にエントリが
  増えるなど、増加はデータの消失ではない）
- **値の比較**: `Value` の中身で比べる。`Value::Undefined` は `ofs` を無視してバイト列だけを
  比べる（上記の実測）。`display_value()` の文字列比較は使わない ── 表示用の整形は
  値の違いを丸めうる
- 同じキーのフィールドが複数ある場合（壊れた IFD 等）は、値の多重集合として比べる

### 検査 2: IFD1 サムネイル本体のバイト列一致

書き込み前にサムネイル（`In(1)/JPEGInterchangeFormat` と `JPEGInterchangeFormatLength` が指す
範囲）があれば、書き込み後も同じバイト列のサムネイルがあることを求める。

- オフセットは **Exif APP1 セグメントの中身**（`Exif\0\0` の直後 = TIFF ヘッダ先頭）からの相対値
  として解決する。ファイル全体を `Exif\0\0` で検索する実測用テストの方法は、XMP 等の中に同じ
  バイト列があると誤る可能性があるので本番では使わない
- 範囲がセグメント外を指すときは、書き込み前なら「元写真のサムネイルが壊れている」として
  比較対象なし（`None`）扱い、書き込み後なら拒否する
- 書き込み前に無ければ何も求めない

### 検査 3: Exif・XMP 以外のセグメントの一致

書き込み前後のそれぞれで、SOS より前のセグメントから **Exif APP1（`Exif\0\0` で始まる APP1）と
XMP APP1（`http://ns.adobe.com/xap/1.0/\0` で始まる APP1）を除いた列**を作り、
マーカーと中身のバイト列が順序を含めて一致することを求める。

- 本ツールはこれらのセグメントを触らないので、一致しなければ即異常
- ICC（APP2）・IPTC（APP13）・Extended XMP（`http://ns.adobe.com/xmp/extension/` の APP1）・
  JFIF APP0・量子化／ハフマン表がここで守られる
- 画素データ（SOS 以降）の一致は既存の検査（`replace_verified` 冒頭）が受け持つ

### 読めない場合の扱い

| 書き込み前の状態 | 扱い |
|---|---|
| Exif APP1 が無い | 検査 1・2 は比べるものが無いので通す。検査 3 は行う |
| Exif APP1 があり、kamadak-exif で読める | 検査 1〜3 を行う |
| Exif APP1 があり、kamadak-exif で読めない | **保存を拒否する** |
| 書き込み後の Exif を kamadak-exif で読めない | 保存を拒否する |

3 行目は利用者判断（2026-09-29）。比べる基準が取れない以上、消えたかどうかを判定できない。
現行はこの場合も `read_exif_info` が `ExifInfo::default()` を返して前後とも空で一致し、素通りする。
**この素通りこそがメタデータ編集 spec が問題視した穴**なので、`read_exif_info` は検証に使わない。

### エラー文面

既存の文面と同じく「何が起きたか」を示し、元写真が無事であることは `write_metadata` の
外側の文脈（「元ファイルは変更していません」）が伝える。

- 検査 1: 「既存の Exif が保存で失われるため中止しました: `<キー>` ほか N 件」。キーは
  kamadak-exif の表記（例 `GPSLatitude`）で、最大 3 件まで列挙する
- 検査 2: 「Exif のサムネイルが保存で変わるため中止しました」
- 検査 3: 「Exif・XMP 以外のメタデータ（`<マーカー名>`）が保存で変わるため中止しました」
- 読めない場合: 「既存の Exif を検証できないため中止しました」

### 置き場所

- 比較処理は新しいモジュール `core/src/metadata/preserve.rs` に置く。入力は書き込み前後の
  **バイト列**で、ファイルには触らない（単体テストで前後を直接組み立てられるようにするため）
- `atomic::verify` は既存の 1・2 番目の検査の後に `preserve::check(original, written)` を呼ぶ。
  `original` は `replace_verified` が既に持つ元写真のバイト列、`written` は**一時ファイルを
  ディスクから読み戻したバイト列**（メモリ上の `patched` ではなく、実際に rename されるものを見る）
- `read_exif_info` を使う現行の 3 番目の検査は削除する（検査 1 がその上位互換）

## 検討した案

| 案 | 不採用の理由 |
|---|---|
| Exif APP1 のバイト列を直接照合する | タグ 1 つの追加で後方のデータが丸ごとずれ、照合のためにオフセットを付け直す処理を自前で書くことになる。フィールド単位の比較で目的は足りる |
| `little_exif` をやめ、IFD0 だけを自前で書き換える | 消失の原因そのものを断てるが、実質 Exif 書き込み器の自作で範囲を大きく超える |
| 増えたフィールドも拒否する | 編集対象を初めて書くときの正常な増加を拒否してしまう。増加はデータの消失ではない |
| 読めない場合は従来の 9 項目比較で保存を許す | 検証されない経路が残り、本 spec の目的に反する（利用者判断で不採用） |

## テスト

`preserve::check` に書き込み前後のバイト列を直接渡す単体テストを中心にする。
書き込み後のバイト列はフィクスチャのコピーから対象を消す・変えることで作る。
**各拒否ケースでは、対象が書き込み前に実在することを先に assert する**
（対象がもともと無いせいで通る偽の成功を防ぐ）。

| ケース | 期待 |
|---|---|
| 編集対象外のタグ（例: GPS 系、無ければ `Make`）が消えた | 拒否。文面にタグ名が出る |
| 編集対象外のタグの値が変わった | 拒否 |
| サムネイル本体が変わった／消えた | 拒否 |
| ICC（APP2）などのセグメントが消えた／中身が変わった | 拒否 |
| Exif APP1 はあるが kamadak-exif で読めない | 拒否 |
| 編集対象の 5 タグだけが変わった／増えた／消えた | 通す |
| `JPEGInterchangeFormat` だけが変わり、サムネイル本体は同じ | 通す |
| Exif をもともと持たない | 通す |

- **誤拒否しないこと**: 既存の結合テスト（`core/tests/metadata_integration.rs`。Lightroom 形式の
  フィクスチャへの書き込みを含む）がそのまま通ること。`a_file_whose_exif_cannot_be_parsed_is_refused_without_being_modified`
  はメタデータ編集の判断の前提なので残す
- **検査が効いていることの確認**: 実装後に検査 1〜3 を一時的に無効化し、対応する拒否テストが
  落ちることを実測する
- **実写真**: `docs/tmp/` の Lightroom 書き出し写真（APP13・ICC 付き）のコピーへ実際に保存を
  通し、拒否されないことを確認する
- **フィクスチャ**: 実測では `exif-only.jpg`・`lightroom-xmp.jpg` ともにサムネイル
  （`JPEGInterchangeFormat` あり）を持つが、**ICC（APP2）を持たない**。検査 3 の拒否ケースは
  テスト内でセグメントを足した入力を組み立てる（`img-parts` で APP2 を挿入）ことで作る。
  フィクスチャファイルの追加が要るかは実装計画で決める

## メタデータ編集 spec への反映

「この保証の実際の強度」の節（ブランチ最終レビュー I-3 の記録）を次の内容に書き換える。

- 検査が比べる範囲（本 spec の検査 1〜3）と、それでも検知しない範囲（MakerNote 内部の
  オフセット整合、XMP 内部の保全）
- 「ゲート自体の強化は次のブランチの仕事」の一文は、本 spec へのリンクに置き換える
