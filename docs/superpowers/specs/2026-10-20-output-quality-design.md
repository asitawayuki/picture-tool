# 書き出し品質の改善 設計

**日付**: 2026-10-20
**対象**: `core/src/lib.rs`（エンコード・サイズ制限・アルファ）、`core/src/decode/`（入力 ICC）、
`core/src/exif_frame/`（ロゴと文字の合成）、`core/Cargo.toml`、
`gui-frontend/src/lib/panels/ConvertPanel.svelte` と `cli/src/main.rs`（背景色の表示）、README、
出力幅上限 spec（`2026-08-12-output-width-limit-design.md`）の誤記訂正

## 背景と目的

利用者は Lightroom Classic（以下 LrC）の書き出しと比べ、本ツールの JPEG が
**品質を下げたときに色が崩れる**ことに気づいた（LrC は品質 20% でも破綻しない）。
調べると原因はコードの不具合ではなく、エンコーダとその周辺の「手抜き」だった。
あわせて変換パイプライン全体を監査し、利用者の写真に実際に効く 7 件を本 spec で直す。

**目的**: LrC の書き出しに近い画質とファイルサイズにする。具体的には次の 4 点。

- 低品質でも色が破綻しない
- 同じ画質ならファイルが小さい
- 広色域の写真の色が正しい
- Exif フレームのロゴと文字がきれいに出る

### 実測（すべて `docs/tmp/20260328-DSC05024.jpg` で測った。LrC 書き出し・sRGB・7008×4672・ぼけの多い桜）

| 現行 品質 60 | 1,233KB | 42.8dB |
| 現行 品質 60 と同じ画素を、ハフマン最適化して書く（Pillow で計測） | 797KB | 42.8dB |

## 決定事項と、捨てた案

| 論点 | 決定 | 捨てた案と理由 |
|---|---|---|
| エンコーダ | **`jpeg-encoder` 0.7.1**（純 Rust）に替える。量子化テーブルを自分で渡し、ハフマン最適化を有効にし、サンプリングを指定し、ICC と Exif を埋め込む | `image` の `JpegEncoder`: ハフマン最適化・サンプリング・テーブル指定のどれも無い。/ mozjpeg（C）: 画質は最良級だが、C のビルド要件が増える。Windows の libdav1d で苦労した直後であり、`jpeg-encoder` で LrC 20% と同じテーブルをバイト単位で再現できた（試作）ので不要 / jpegli: Rust から安定して使える形が無い |
| 品質の目盛り | **LrC に「似せる」**（利用者判断 2026-10-20）。1〜100 の数値は残す。品質 20 で LrC 20% と同じテーブルになるようにし、ほかの値はそこから作る（「品質の目盛り」の節） | LrC と同じ数値にする: 13 段階すべての書き出しが要る。利用者は「現状は似せるだけで十分」と判断した / LrC の高品質側の書き出しを足し、基準点を 2〜3 点にする: 利用者が不要と判断した（2026-10-20）。手元にある LrC 85% の 1 枚は、合否の基準にせず参考の比較にだけ使う / 標準テーブルを今と同じ式でスケールし、要素ごとに上限だけを設ける: 高品質側は今と同一になり既定値 90 の退行は起きないが、品質 20 が LrC 20% から離れ、「LrC に似せる」という目的に合わない |
| Exif | **位置情報（GPS）と、撮影者や機材個体を特定しうるタグ（シリアル番号・所有者名・作者名）を消して、それ以外を出力に残す**（利用者判断 2026-10-20）。消すもの・書き換えるものは「Exif」の節 | 全部残す: 位置情報が漏れる。/ 今のまま全部捨てる: 出力ファイルで撮影情報が見えない |
| 色管理 | 入力の ICC が sRGB 以外なら、デコード直後に **moxcms** で sRGB へ変換する。出力には常に sRGB の ICC を埋め込む | ICC をそのまま出力へ写す: Exif フレームの色（背景・文字）は sRGB で指定しているので、写真と枠の色空間が食い違う。Instagram 側でも ICC の扱いが一定しない |
| 範囲 | 監査で見つかった 11 件のうち、**1〜7 だけを本 spec で扱う**（利用者判断 2026-10-20） | 残り 4 件（縮小後のシャープ化・リニア光での縮小・JPEG XL / AVIF の色管理と HDR・GUI プレビューが本番と別の処理）は効果が小さいか、好みで決まる。「やらないこと」を参照 |

## 付随処理の失敗

ICC と Exif の処理が失敗しても、1 枚の変換は失敗させない。**警告（`warnings`）に積み、その情報なしで書く**。
対象は ICC の読み取り・ICC の変換・Exif の読み取り・Exif の組み立て・埋め込みのすべてである。
画素は正しく作れているのに付随情報のせいで変換全体が失敗すると、今は変換できている写真が新たに失敗するようになるためである。

例を挙げる。

- ICC は読めたが、moxcms が変換を作れない（CMYK の ICC、未対応の LUT 型など）→ 変換せず sRGB とみなす
- kamadak-exif の `Writer` が `Value::Unknown` のタグを拒否する → そのタグを落として組み直す。それでも失敗したら Exif なしで書く
- `add_exif_metadata` が 65,528 バイトを超えて `Err` を返す → Exif なしで書く

例外は、デコードのメモリ予算の検査（5 の節の `reserve`）だけである。予算を超えたら、今と同じく 1 枚の `Err` にする。

## 範囲

監査結果の番号（利用者に示した表）で書く。

| # | 問題 | 本 spec での扱い |
|---|---|---|
| 1 | エンコーダ: ハフマン最適化なし・標準テーブル・4:4:4 固定 | エンコーダを替え、目盛りを作り直す |
| 2 | Exif フレームの横長 SVG ロゴ（SONY・FUJIFILM）が 4〜5 倍に引き伸ばされてぼやける | 表示する高さで直接ラスタライズする |
| 3 | SVG ロゴの画素がプリマルチプライドのまま、ストレートアルファとして扱われる | demultiply する |
| 4 | Exif の文字の縁でアルファを二重に掛けている（コードから確定） | 合成式を直す |
| 5 | 入力の ICC を無視し、出力にも埋め込まない（JPEG / PNG / WebP） | sRGB に変換し、sRGB の ICC を埋め込む |
| 6 | 透過を背景色で合成しない（crop / quality と、厳密な 4:5 の pad） | 全モードで `bg_color` に合成し、背景色を全モードで選べるようにする |
| 7 | サイズ制限の探索が品質を 5 刻みで下げ、60 で止まる | 二分探索にし、下限を新しい目盛りで決め直す |

### やらないこと

- 縮小後のシャープ化（LrC の「画面用シャープ」相当）: 強さは好みで決まる。別途、利用者と決める
- リニア光での縮小: 実写での差は 0.17 階調（8bit 換算）で、新しい依存が要る
- JPEG XL / AVIF の色管理・HDR: README に既知の制限として書いてある。本 spec の ICC 変換は JPEG / PNG / WebP だけに入れる。
  JPEG XL は ICC を取り出す経路（`JxlDecoder::icc_profile()`）があるので同じ関数に通せるが、HDR（PQ / HLG）のトーンマップが要る入力と区別できない。そのため一緒に別 spec で扱う
- GUI プレビュー（`generate_exif_frame_preview_base64`）を本番と同じ処理にすること。ただし 2〜4 の修正は共通の描画コードに入るので、プレビューにも自然に効く
- PNG の gAMA / cHRM / sRGB チャンクによる色指定（iCCP だけを見る）
- 16bit → 8bit のディザ
- XMP・IPTC を出力へ写すこと（「Exif」の節）
- 品質の数値を LrC と完全に一致させること

## 1. エンコーダと品質の目盛り

### エンコーダ

`encode_jpeg_rgb` を `jpeg-encoder` = "=0.7.1" による実装に替える。設定は次のとおり。

- 量子化テーブルは `QuantizationTableType::Custom` で、輝度用と色差用を自前で渡す（目盛りの節）
- `set_optimized_huffman_tables(true)`
- サンプリングは目盛りの節に従い、**`set_sampling_factor` を必ず明示する**。
  `Encoder::new(w, quality)` は渡した品質で既定のサンプリングを決める（90 未満なら 4:2:0）。
  `Custom` テーブルを使っても、この既定は効く
- **`set_chroma_subsampling_method(ChromaSubsamplingMethod::Average)` を必ず指定する**。
  既定の `Nearest` は 2×2 ブロックの左上 1 画素だけを使うので、色差の縁がギザギザになる
- `add_icc_profile` で sRGB の ICC を、`add_exif_metadata` で Exif（「Exif」の節）を埋め込む
- ベースライン（プログレッシブにしない）。LrC の書き出しもベースラインだった

**サムネイルとプレビュー**（**実装者側（本 spec）の判断**）: `encode_jpeg_rgb` には本番の出力のほかに 3 つの呼び出し元がある。
`generate_thumbnail_base64`（品質 75）、`generate_exif_frame_preview_base64`（85）、lib.rs:626 付近のプレビュー（90）である。
これらも新しいエンコーダと新しい目盛りに揃え、品質の数値はそのまま使う。
ただし ICC と Exif は埋め込まない。webview に表示するだけで、sRGB として扱われるので要らない。
関数は「画素と品質から JPEG を作る共通部分」と「本番用に ICC と Exif を足す部分」に分ける。
引数で切り替えるか、関数を 2 つにするかは実装者が決める。

**`Custom` テーブルの並び**: `jpeg-encoder` の `Custom` は**自然順（行優先）**で受け取り、DQT へは zigzag で書く。
上の LrC のテーブルは zigzag 順なので、並べ替えてから渡す。試作では並べ替えたうえで、
出力の DQT がバイト単位で LrC と一致することを確認した。

**ライセンス**: `jpeg-encoder` は `(MIT OR Apache-2.0) AND IJG`。IJG ライセンスは、バイナリを配布するとき
文書に「this software is based in part on the work of the Independent JPEG Group」と書くことを求める。
README の「ライセンス」節に書く。

### 品質の目盛り

`--quality`（GUI の「品質」スライダー）の 1〜100 は残す。次の性質を満たすテーブルの作り方を、実装者が決める。

1. **品質 20 のテーブルは、上の LrC 20% のテーブル（輝度・色差）と完全に一致する**
2. **品質 100 は全要素 1**
3. **単調性**: 品質を下げると、どのテーブルのどの要素も増えるか変わらない。
   これにより、出力サイズも（ほぼ）単調に減る。サイズ制限の二分探索はこれを前提にする（7 の節）
3a. **全要素が 1〜255**: `jpeg-encoder` 0.7.1 は `Custom` の値を 2048 まで受け付ける。
   しかし DQT には下位 8bit しか書かない（`get()` が `(v >> 3) as u8`）。
   そのため 256 以上の値は、エラーにならずに壊れた JPEG を作る（300 なら DQT 上は 44 になる）
4. **品質 1 でも色が破綻しない**: サンプル写真のぼけ（下の検証手順）で、色相のブロック状の飛びとグレー化が起きない。
   LrC 20% が高周波を 12 で頭打ちにしているのと同じ考え方で、要素ごとに上限を設けてよい
5. **既定値 90 で、現行より悪くならない**: 検証に使う**すべての**写真（下の検証手順。サンプル写真と、傾向の違う写真）を quality モードで書き出したとき、
   新しい品質 90 は**ファイルサイズが現行の品質 90 以下で、PSNR が現行の品質 90 以上**であること。
   許容幅は、サイズが現行の 1.01 倍まで、PSNR が現行 −0.1dB まで。
   1 枚でも外れたら、下の優先順位に従う
   ハフマン最適化だけで約 35% 小さくなるので、達成できる見込みがある（推測。実装時に実測する）

**優先順位**（**実装者側（本 spec）の判断**）: 1・2・3・3a は絶対条件である。4 と 5 は s(q) の形・上限・サンプリングの閾値で合わせる。
それでも 4 と 5 が両立しないときは、どちらかを勝手に緩めない。
実測値を実施メモに残し、利用者に判断を仰ぐ。

作り方の一例（**拘束しない**）: LrC 20% のテーブルを基準形とし、品質に応じた倍率 s(q) を掛けて丸め、
1 以上・上限以下に収める。s(20) = 1 とし、q = 100 で全要素 1 になるように s を選ぶ。
4 と 5 は s の形と上限で調整する。
ただし参考データが示すとおり、LrC は高周波の刻みを低周波よりずっと遅く細かくする（20% と 85% で 12、さらに高い品質で 8）。
単純な倍率では高品質側のファイルが LrC より大きくなりやすいので、高周波を低周波より遅く細かくする形も検討する。
その場合も、高周波をある品質まで据え置いてから品質 100 で一気に 1 にするような、サイズが急に跳ねる形は避ける。

**サンプリング**: 品質 50 未満は 4:2:0、50 以上は 4:4:4（**実装者側（本 spec）の判断**）。
LrC は 20% で 4:2:0、85% で 4:4:4 だった（実測）。どこで切り替わるかは確かめていない。
閾値は 5 の検証で見直してよい。見直した場合は実施メモに残す。

**既存の設定値**: GUI に保存された品質の値は数値のまま引き継ぐ。数値の意味が変わることは README に書く。
移行処理は行わない。

### 検証手順（目盛り）

- サンプル写真の切り抜き `400x300+500+2800`（ぼけの領域）を、品質 1・5・10・20・40・60・90・100 で書き出す。
  元画像と並べ、彩度を強調した画像（`magick ... -modulate 100,300`）を利用者に見せる
- 実測値（サイズ・PSNR・各品質のテーブルの最大要素）を実施メモに表で残す
- 性質 5 と、サイズ制限の下限（7 の節）の換算は、サンプル写真 1 枚では決めない。
  サンプル写真はぼけが多く、高周波が少ないためである。
  LrC 20% の形は高周波が 12 で平らなので、高周波の多い写真では、新しい品質 90 が現行の品質 90 より大きくなりうる。
  傾向の違う写真で測ること。高感度のノイズが多い写真と、細部の多い風景を、それぞれ 1 枚以上使う。
  写真は実装時に利用者に提供を頼む。LrC で強く圧縮した書き出しではなく、元に近いものを使う。
  利用者の手元には LrC から書き出した JPEG XL があるので、候補として使えるか（ノイズや細部の傾向、書き出し時の圧縮の強さ）を実装時に確かめる
- 単調性と「全要素が 1〜255」は、テーブル生成関数の単体テストで固定する（全品質 × 全要素）
- 「品質 20 が LrC 20% と一致」は、出力 JPEG の DQT を読んで比べるテストで固定する
- 参考（合否の基準にしない）: 新しい品質 85 のテーブルを LrC 85% のテーブルと並べ、要素ごとの比を実施メモに残す

## 2・3. Exif フレームのロゴ

### 2. 表示する高さで直接ラスタライズする（メーカーロゴとレンズロゴ）

現状、`core/src/exif_frame/mod.rs:262` 付近ではロゴを `logo_size = min(バー高, バー幅) * 3/5` を**長辺**として読み込む。
その後 `render_exif_bar`（mod.rs:355 付近）で、高さ `0.45 × バー高` に Lanczos3 で再拡大している。
横長ロゴ（SONY 5.68:1、FUJIFILM 6:1）は長辺が幅になるので、読み込み時の高さが小さくなりすぎる。
その結果、約 `0.75 × アスペクト比` ≒ 4.3〜4.5 倍に拡大される。この倍率はバー高に依存しないので、どの解像度でも起きる。

- `--max-width 1080 -e`（Instagram 向けの標準的な使い方）では、高さ約 4px で描いたものを 108×19 に拡大している。
  SONY の文字は判読できない（監査で実測。比較画像あり）
- **直し方**: 表示する高さ（`0.45 × バー高`）を先に決め、SVG をその高さで直接ラスタライズする。再リサイズは無くす。
  PNG ロゴ（gmaster）は今のまま（縮小 1 回だけで、実害なし）でよい
- **レンズロゴも対象にする**。レンズロゴも同じ `logo_size`（長辺）で読み込まれている（mod.rs:306 付近）。
  そのうえで `render_exif_bar` の中で、高さ `secondary_size_base × 1.2` に再リサイズされる（mod.rs:441-447 付近）。
  利用者が差し替えた横長の SVG レンズロゴ（README で差し替えを案内している）も、同じようにぼやける。
  ただし表示する高さはフォントサイズから決まり、読み込みより後に計算されている。
  そのため、表示高さを先に求めてから読み込むよう、計算の順序を入れ替える。
  入れ替え方（読み込みを `render_exif_bar` の中に移すか、`secondary_size_base` の計算を前に出すか）は実装者が決める
- **誤記の訂正**: `2026-08-12-output-width-limit-design.md` の「同梱ロゴは…拡大は起きない」（184〜186 行付近）は、
  横長 SVG では成り立たない。この節に訂正の注記を足し、本 spec へリンクする

### 3. プリマルチプライドを demultiply する

`logo.rs` の `load_svg_from_bytes`（95 行付近）は `RgbaImage::from_raw(..., pixmap.data().to_vec())` で画像を作っている。
しかし tiny-skia の `Pixmap::data()` は**プリマルチプライド** RGBA である。
このため黒背景用の白ロゴ（`_light`）では、アンチエイリアスの縁が暗く痩せる。
`pixmap.pixels()` の各画素を `demultiply()` してから `RgbaImage` に詰める。

### 検証（ロゴ）

- 原寸と `--max-width 1080` の両方で、白背景と黒背景のバーを書き出す。
  ベクタから直接ラスタライズした基準画像（`magick` で同じ高さに描いたもの）と並べて利用者に見せる
- テスト: 横長ロゴを読み込んだ画像の高さが表示高さと一致すること（再拡大していないこと）を固定する。
  白ロゴの縁の画素値が、demultiply していれば取るはずの値になることを固定する。
  直す前のコードに戻すと落ちることを確かめる

## 4. Exif の文字の合成

`text.rs:135-155`（`draw_text_on_image`）は、透明バッファ（0,0,0,0）に「色 × coverage + 既存 × (1 − coverage)」を書いている。
これは RGB がプリマルチ済みでアルファが coverage の状態である。
それを `imageops::overlay`（ストレートアルファとして合成）でキャンバスに重ねている。
その結果、縁は `色·c² + 背景·(1−c)` になる。正しくは `色·c + 背景·(1−c)`。

- この結論はコードから一意に導けるので、直すことは確定している
- 単体テストで固定する。同じ文字列を 2 通りに描いて比べる。1 つは不透明な背景に直接描いた結果、もう 1 つは透明なバッファに描いてから重ねた結果である。
  画素が許容差内で一致すれば合格とする。修正前のコードでは縁の画素が食い違って落ちることを確かめる
- 合成はストレートアルファの over 合成（`out_a = a + ea(1−a)`、`rgb = (c·a + e·ea·(1−a)) / out_a`）にする。
  回転して貼る経路（Right / Left 配置）でも同じ関数を通す
- 本番で使われていない `draw_text_rotated_90`（text.rs:164）も同じ式を持っている。呼び出し元が無いことを確かめて消す

## 5. 入力の ICC

- **対象**: JPEG / PNG / WebP
- `decode::open`（`core/src/decode/mod.rs:91`）は今 `ImageReader::...decode()` で画素だけを取っている。
  これを `into_decoder()` 経由にし、`icc_profile()` を取り出す
- **メモリ予算の検査を残す**: `ImageReader::decode()` は内部で `limits.reserve(decoder.total_bytes())` を呼んでいる。
  一方 `into_decoder()` はこれを呼ばない。
  そのため、JPEG XL の経路（mod.rs:95）と同じく、`from_decoder` の前に `image::Limits::default().reserve(decoder.total_bytes())?` を挟む。
  挟まないと、寸法だけが巨大な PNG（デコンプレッションボム）で 512MiB の上限が外れ、プロセスごと落ちうる。
  JPEG / PNG / WebP にはこれを固定するテストが無いので、足す。
  テストでは、寸法だけ巨大で中身は正当な PNG が `Err` になることを確かめ、`reserve` を外すと結果が変わることを実測する
- ICC があり、それが sRGB でなければ、moxcms で sRGB に変換する。
  レンダリングインテントは**相対的色域維持**とする。AdobeRGB や ProPhoto のようなマトリクス型のプロファイルには知覚的レンダリング用の表が無いので、どちらを選んでも結果は同じになる。
  明示しておけば、検証で ImageMagick と比べるときに条件を揃えられる。
  moxcms 0.8.1 は `image` 0.25.10 経由ですでにビルドされている（`cargo tree -i moxcms`）。core の直接依存に足すだけでよい
- **変換する画素形式**: 8bit の画像（`Rgb8` / `Rgba8`）は 8bit のまま、16bit の画像（`Rgb16` / `Rgba16`）は 16bit のまま変換する。アルファはそのまま残す。
  グレー（`Luma*`）の画像に Gray の ICC が付いているときは、グレーとして変換する。
  画素形式と ICC の色空間が合わないものは変換せず、sRGB とみなして警告する（下の「付随処理の失敗」）。
  たとえば CMYK の ICC がこれにあたる（zune-jpeg は CMYK の JPEG を RGB にして返すが、ICC は CMYK のまま）
- **変換は行単位で行う**: moxcms の `TransformExecutor::transform(&self, src: &[V], dst: &mut [V])` は、サンプル数が合っていればどんな長さのスライスでも受け取る。
  そこで 1 行分（または小さな帯）の作業バッファで変換し、元のバッファへ書き戻す。画像 1 枚分の変換バッファは確保しない。
  そのため、ICC 変換のためにメモリ予算を増やして数える必要はない
- **テストは許容差つきで書く**: `image` が moxcms を既定の feature で依存しているため、AVX / SSE の経路は core 側から切れない。
  CPU によって 1 階調ほど結果が変わりうる（未確認）
- ICC が無いか、壊れていて読めないときは sRGB とみなす（今と同じ動き）。読めない ICC は `warnings` に積む。
  **`core` は `eprintln!` しない**（CLAUDE.md の不変条件）
- **警告の返し方**（**実装者側（本 spec）の判断**）: `decode::open` は `Result<DynamicImage>` しか返せない。
  そこで、警告も返す関数（たとえば `open_with_warnings`）を新しく作る。`process_image`（lib.rs:375）はこれを使う。
  `decode::open` は、その関数を呼んで警告を捨てる薄い包みとして残す。
  そうすれば、サムネイルとプレビューの経路（`open_image_oriented`、lib.rs:289）はシグネチャを変えずに済む。
  サムネイルとプレビューでは警告を捨ててよい
- 「sRGB かどうか」の判定方法（プロファイルの説明文字列か、色度点と TRC の比較か）は実装者が決める。
  LrC が埋め込む `sRGB IEC61966-2.1` を、無駄に変換しないこと
- `decode::open` はサムネイルとプレビューの経路（`open_image_oriented`）からも呼ばれるので、そこの色も正しくなる。意図した変化である
- **出力**: 常に sRGB の ICC を埋め込む。中身は moxcms が作る sRGB プロファイルか、同梱するプロファイル（実装者が選ぶ）。
  LrC の出力と同じく、全出力に付ける

### 検証（ICC）

- 4 色パッチ（sRGB 値 200,60,60 / 60,160,90 / 90,110,200 / 210,170,120）を AdobeRGB と ProPhoto の ICC 付き JPEG にする
  （監査と同じ作り方: ImageMagick の `-profile /usr/share/color/icc/colord/AdobeRGB1998.icc` と `ProPhotoRGB.icc`）。
  変換結果を、ImageMagick で正しく sRGB に変換した値と比べる。比べるときは ImageMagick にも相対的色域維持（`-intent relative`）を指定する
  - 監査での現行値と正解（AdobeRGB）: 赤 200,60,59 → 正しくは 232,57,56、緑 60,160,90 → 0,161,85
  - 許容差は JPEG の誤差を見込み、実装者が決めて実施メモに残す
- sRGB の ICC 付き入力（サンプル写真）は、変換が走らず現行と同じ画素になること
- 出力に sRGB の ICC が入っていること
- PNG（iCCP 付き）・WebP（ICCP チャンク付き）でも同様に確かめる
- テスト用のフィクスチャは小さく作る（パッチ画像を数十 px で）

## 6. 透過の合成

- `process_image` の中で、デコードと向きの適用の直後に「アルファがあれば `bg_color` に合成して RGB8 にする」ステップを 1 つ入れる。
  合成はストレートアルファの over。これ以降の処理（縮小・pad・crop・フレーム・エンコード）はすべて RGB だけを扱う
- これで次の 3 つが同時に消える
  - crop / quality で、透けている部分に隠れていた色がそのまま出る
  - 厳密な 4:5 の pad で、早期 return のために背景色が効かない
  - RGBA のまま縮小することで、透過の縁に色が滲む
- **サムネイル・プレビューには入れない**（変換の経路だけ）
- **背景色を全モードで選べるようにする**（利用者判断 2026-10-20）。今は GUI が背景色の選択を pad のときしか出さない（`ConvertPanel.svelte:94-105`）。
  そのため、以前 pad で黒を選んだ利用者が crop / quality に切り替えると、画面に見えない黒で透過が合成されてしまう
  - GUI: 背景色の選択を `{#if config.mode === "pad"}` の外へ出し、全モードで表示する。
    pad 以外では「透過部分の色」として効くことが分かる表示にする（文言は実装者が決める）
  - CLI: `--bg-color` のヘルプ（`cli/src/main.rs:28`「パディング時の背景色」）を、余白と透過部分の両方に効く書き方にする
  - README: 「変換モード」の表と「CLIオプション一覧」を同じように直す
  - GUI の確認は Playwright（`cd gui-frontend && bun run e2e`）で、crop / quality でも背景色の選択が表示されることを固定する
    （e2e のロール参照は容器へスコープする）
- 検証: 透過部分の裏の RGB が赤（255,0,0, α=0）の PNG と、半透明（α=128）の緑の PNG を用意する。
  crop / quality / pad（厳密な 4:5 を含む）× `-b white` / `-b black` で、出力の画素が背景色、または正しく混ざった値になることをテストで固定する

## 7. サイズ制限の探索

- 現行（`encode_within_size_limit`、lib.rs:763）は、初期品質から 5 ずつ下げて最大 7 回エンコードし、品質 60 で止める。
  上限 6MB のサンプルでは品質 95（6.70MB）の次が 90（4.42MB）になり、予算の約 30% が使われない
- **新しい動き**:
  1. 初期品質でエンコードし、上限以下ならそれを採用する（ほとんどの写真はここで終わる）
  2. 超えたら、[下限, 初期品質 − 1] の整数を二分探索し、**上限以下に収まる最大の品質**を採用する
  3. 下限でも超えたら、下限の結果を書き、今と同じく「収まらなかった」として警告する
- **下限は「現行の下限 60 と同じ画質」に換算した値**: 「下限の画質を変えない」ための換算である。
  目安は 20 で、サンプル写真では現行の品質 60 と新しい目盛りの 20（LrC 20% 相当）の PSNR がほぼ等しい（42.8dB と 42.6dB）。
  品質の目盛りを作り終えたら、検証に使う**すべての**写真で換算し直す。
  写真ごとに、新しい目盛りで PSNR が現行の品質 60 以上になる最小の品質を求め、**そのうち最も高い値を下限にする**。
  どの写真でも、下限の画質が現行の下限を下回らないようにするためである
- 初期品質が下限より低いときは、初期品質だけで終える（今と同じ考え方）
- エンコード回数は最悪でも `1 + ceil(log2(初期品質 − 下限))` 回。初期 90 なら 8 回で、今の最悪 7 回とほぼ同じ
- 単調性（目盛りの性質 3）が崩れると二分探索の答えが最大とは限らなくなるが、「上限以下に収まる」ことは常に守られる。
  これは実装のコメントに書く
- 戻り値の `final_quality`（初期品質より下げたときの値）と、警告の文面（`Size limit not met: ... even at minimum quality {}`）の形は変えない。
  README の「サイズ圧縮」節は新しい動きに書き換える

## Exif

**消すもの・書き換えるもの**（**実装者側（本 spec）の判断**。利用者が決めたのは「位置情報と、撮影者や機材個体を特定しうるタグを消す」）。

| 対象 | 扱い | 理由 |
|---|---|---|
| GPS IFD（`GPSInfo` ポインタと、その下のタグすべて） | 消す | 利用者の判断 |
| `Orientation` | 元にあれば 1 にする。無ければ足さない | 画素はすでに回転済み。残すと二重に回る |
| IFD1（サムネイル） | 消す | 元写真の構図のサムネイルで、出力（4:5・フレーム付き）と食い違う |
| `MakerNote` | 消す | 中身がファイル先頭からの絶対オフセットを持つことがあり、書き直すと壊れる。撮影情報の標準タグは本体 IFD と Exif IFD にある |
| `PixelXDimension` / `PixelYDimension` | 出力の寸法に書き換える（無ければ足さない） | 実際の画素数と食い違わないように |
| `ColorSpace` | 元にあれば 1（sRGB）にする。無ければ足さない | 出力は常に sRGB |
| 撮影者や機材個体を特定しうるタグ: `BodySerialNumber`（0xA431）・`LensSerialNumber`（0xA435）・`CameraOwnerName`（0xA430）・`Artist`（0x013B）・`XPAuthor`（0x9C9D）・`CameraSerialNumber`（0xC62F。DNG 由来の機体シリアル。2026-10-21 追加）。本来と違う IFD に置かれていても番号で照合して消す | 消す | 利用者の判断（2026-10-20、`CameraSerialNumber` は 2026-10-21）。手元で撮影情報を見る目的には要らず、出力を人に渡したときに漏れる。`Copyright` は撮影者が権利表示として意図して付けるものなので残す（**実装者側（本 spec）の判断**） |
| 値がファイル内のオフセットであるタグ（`SubIFDs` 0x014A、`DNGPrivateData` 0xC634、`OffsetSchema` 0xEA1D、`StripOffsets` / `TileOffsets` 系など） | 消す | 組み立て直した TIFF の中では、どこも指さない参照になる。kamadak-exif は `SubIFDs` の先を辿らず、数値のまま写してしまう |
| 上記以外の本体 IFD・Exif IFD・Interop IFD のタグ | そのまま残す | 撮影情報（カメラ・レンズ・設定値・日時・タイトル・コメント）を見えるようにする |

- **XMP と IPTC は写さない**（**実装者側（本 spec）の判断**）。LrC の XMP は位置情報を持つことがあり（`exif:GPSLatitude` 等）、
  中身を選り分けると Exif と同じ手間がもう一つ増える
- **入力**: JPEG / PNG / WebP / AVIF は kamadak-exif の `read_from_container` で取れる。
  AVIF は HEIF として読まれ、`core/tests/jxl_avif_input.rs` の `camera_info_is_read_from_jxl_and_avif_exif` が `exif_o6.avif` で固定している。
  JPEG XL は既存の `decode::jxl_raw_exif` で取れる
- Exif が無い、または壊れていて読めない入力は、Exif なしで書く。読めなかったことは `warnings` に積む
- **Exif を書かない場合**（**実装者側（本 spec）の判断**）: 上の表に従って消し、書き換えた後に、次のタグしか残らなければ Exif を書かない。
  - 書き換えたタグ（`Orientation`・`ColorSpace`・`PixelXDimension`・`PixelYDimension`）
  - 構造や形式だけを表すタグ（`ExifVersion`・`FlashpixVersion`・`XResolution`・`YResolution`・`ResolutionUnit`・`YCbCrPositioning`・`ComponentsConfiguration`・`ExifIFDPointer`・`InteropIFDPointer` と Interop IFD の中身）

  1 つでもほかのタグ（`Make`・`Software`・`DateTime` など）が残れば書く
- **書き出し**: 新しい TIFF ブロックを組み立て直す（既存のバイト列を部分的に切り貼りしない）。kamadak-exif の
  `experimental::Writer` か、`little_exif`（既存依存。SHORT→LONG の正規化を起こすことがメモに残っている）か、どちらで組むかは実装者が決める
- メタデータ編集機能（元写真へ書き込む `core/src/metadata/`）は触らない。本節は変換の出力だけの話

### 検証（Exif）

- GPS とシリアル番号付きの JPEG（フィクスチャ）を変換し、出力に GPS IFD と表の「撮影者や機材個体を特定しうるタグ」が無いこと、`Copyright` が残ること、`Make` / `Model` / `ExposureTime` / `DateTimeOriginal` 等が残ること、
  `Orientation` が 1 であること、`PixelXDimension` が出力の幅であることをテストで固定する
- Orientation 6 の入力で、出力をビューア（Exif の向きに従うもの）で開いても二重に回らないこと
- JPEG XL と AVIF の入力（既存のフィクスチャ `exif_o6.jxl`・`exif_o6.avif`）でも、出力に Exif が載ること、`Orientation` が 1 であることを確かめる。
  GPS 付きの JPEG XL / AVIF のフィクスチャは無いので、GPS が消えることの確認は JPEG で行い、経路が共通であることをコードで確かめる
- 撮って出しの写真（カメラ生成の JPEG。MakerNote・IFD1 を持つ）と LrC 書き出しの両方で確かめる。
  書き出し写真だけでは見えない差があった前例がある（メタデータ書き込み検証 spec）
- 出力を `exiftool` 相当（kamadak-exif で読み直す）で検査し、警告なく読めること
